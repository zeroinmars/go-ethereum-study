# 학습 작업일지: 트랜잭션 실행 흐름과 실제 P2P 노드 관찰

- 기록일: 2026-11-04
- 학습 범위: 테스트용 블록 생성, receipt와 withdrawal, StateProcessor와 StateTransition, geth 실행 및 피어 탐색, raw 트랜잭션의 발신자 복구.
- 진행: 로컬 소스 확인과 질의응답, 사용자의 geth 실행·종료, node-data 용량 및 노드 DB 읽기 전용 확인. geth 소스는 수정하지 않음.

## 스트레스 프로그램의 Commit

`miner/stress/main.go`는 트랜잭션을 대량으로 넣어 노드에 부하를 주는 프로그램이다.

- 트랜잭션을 TxPool에 추가하고 `sent`를 증가시킨다.
- `sent % 256 == 0`이면 `beacon.Commit()`을 호출한다. 256은 테스트의 실행 간격이며 프로토콜 규칙이나 블록당 거래 수가 아니다.
- pending 거래가 4,096개를 넘으면 추가로 Commit하고, 거래를 넣는 루프를 50ms 쉬게 한다.
- `SimulatedBeacon.Commit()`은 출금 큐에서 최대 10건을 꺼내 `sealBlock()`에 전달한다. 실제 네트워크 합의의 최종 확정을 뜻하지 않는다.
- `sealBlock()`은 Engine API의 forkchoiceUpdated → getPayload → newPayload → forkchoiceUpdated 경로로 블록 생성·수용·head 갱신을 진행한다.

`withdrawals.pop(10)`의 10은 ETH 수량이 아니라 내역 개수다. FIFO 순서로 최대 10건을 반환하고 큐에서 제거한다. 대기 내역이 없을 수도 있다.

## Transaction, withdrawal, receipt 구분

- Transaction: 송금·컨트랙트 호출 등 서명된 실행 요청.
- Withdrawal: 검증자의 출금 ETH를 실행 계층 주소에 지급하는 프로토콜 내역. 일반 트랜잭션과 별도의 목록이다.
- Receipt: 트랜잭션을 실행한 결과 기록. 상태, 가스 사용량, 이벤트 로그 등을 담는다.

이더리움의 공식 스테이킹 입금은 Deposit Contract 호출로 시작하지만, withdrawal 지급 자체는 컨트랙트 호출이 아니다. PoW 시절의 uncle 보상 설명은 현재 PoS 실행과 구분한다. Coinbase는 이 문맥에서 거래소가 아니라 블록의 보상·수수료 수령 주소를 뜻한다.

## StateTransition의 위치와 실행 순서

`TransactionToMessage()`는 전송용 메시지를 만드는 함수가 아니다. 각 노드가 트랜잭션을 내부에서 실행할 때 사용할 데이터를 구성한다. TxPool에는 Message가 아니라 Transaction을 보관한다.

```text
블록 생성: TxPool에서 거래 선택 → Message 변환·실행 → 블록 완성
블록 검증: 받은 블록의 거래 → Message 변환·실행 → 결과 검증
```

다른 노드가 만든 블록의 거래는 내 TxPool에 있었을 필요가 없다. 상대 노드도 geth라면 그 노드 내부에서 같은 실행용 변환을 한다.

현재 소스의 주요 경로:

```text
TransactionToMessage
  → ApplyMessage
  → stateTransition.execute
      → preCheck → buyGas
      → IntrinsicGas 계산 및 한도 확인
      → 송금 가능 여부 확인·StateDB 실행 준비
      → executeCall 또는 executeCreate → EVM
      → settleGas
      → 수수료의 팁 지급·ExecutionResult 반환
```

- `buyGas()`는 송금액과 가스비를 감당할 잔액이 있는지 검사하고 가스비를 먼저 차감한다.
- `have`는 현재 잔액, `want`는 필요한 잔액이다. `have.Cmp(want) < 0`이면 잔액 부족 오류다.
- `balanceCheck`는 잔액 검사 금액이고 `mgval`은 먼저 차감할 가스비다. 수수료 상한과 실제 적용 가격에 따라 두 계산이 달라질 수 있다.
- 송금액 이동과 컨트랙트 실행은 이후 EVM 호출에서 수행한다. 실행 후 남은 가스에 해당하는 ETH를 반환한다.
- 결과는 StateDB의 상태 변경과 ExecutionResult의 사용 가스·오류·반환 데이터다. Receipt는 호출한 쪽에서 구성한다.
- 실행 전 유효성 검사 실패와 EVM 실행 중 revert는 다르다. 후자는 실패한 거래로 블록에 포함되고 가스가 부과될 수 있다.
- StateDB 변경과 디스크에 최종 저장하는 단계는 구분한다.

## Raw 트랜잭션 RPC와 서명 복구

```text
eth_sendRawTransaction
  → internal/ethapi/api.go: SendRawTransaction
  → Transaction.UnmarshalBinary: 바이트 디코딩
  → SubmitTransaction
  → eth/api_backend.go: SendTx
  → TxPool.Add 및 검증
  → types.Sender
  → 서명 방식별 Sender
  → core/types/transaction_signing.go: recoverPlain
  → crypto.Ecrecover: 서명과 서명 대상 해시로 공개키 복구
  → Keccak256(pub[1:])의 마지막 20바이트로 발신자 주소 도출
```

Raw 거래에 공개키가 그대로 포함된다는 뜻은 아니다. 디코딩과 공개키 복구는 별도 작업이며, Sender는 복구한 주소를 캐시할 수 있다.

## 실제 geth 실행과 P2P 관찰

실행 위치는 `go-ethereum` 소스 폴더다.

```powershell
go run ./cmd/geth --datadir .\node-data --verbosity 3 --log.vmodule "p2p/*=5" console
```

- `go run ./cmd/geth`: 소스를 빌드하고 실행한다.
- `--datadir`: 로컬 DB와 노드 관련 파일의 저장 위치.
- `--verbosity 3`: 기본 INFO 로그.
- `--log.vmodule "p2p/*=5"`: P2P 로그만 TRACE까지 출력.
- `console`: JavaScript 콘솔을 함께 실행한다.
- 별도 네트워크 옵션이 없으므로 기본 메인넷 설정이다. 저장 폴더 지정은 사설 체인 생성이 아니다.

Geth 단독으로도 DB 초기화, 피어 발견과 연결, TxPool 및 통신 인터페이스 준비는 진행한다. 현재 PoS 체인의 정상적인 동기화와 head 추적에는 합의 클라이언트 연결이 필요하다. StateDB가 자체적으로 계속 거래를 실행하는 것은 아니다.

관찰용 콘솔 명령:

```javascript
net.peerCount
admin.peers
admin.nodeInfo
debug.vmodule("p2p/*=4") // TRACE 숨기고 DEBUG 유지
debug.vmodule("p2p/*=3") // INFO 수준으로 축소
```

발견한 후보 수와 실제 연결된 피어 수는 다르다. 피어 탐색은 시작 시 한 번으로 끝나지 않고 계속 수행한다.

| 로그 | 의미 |
|---|---|
| `>>` / `<<` | 전송 / 수신 |
| PING / PONG | 응답 여부 확인 / 응답 |
| FINDNODE | 대상 ID에 가까운 노드 정보 요청 |
| NEIGHBORS(v4), NODES(v5) | 노드 목록 응답 |
| ENRREQUEST / ENRRESPONSE | 노드 레코드 요청 / 응답 |
| Starting p2p dial | 연결 시도 |
| Adding / Removing p2p peer | 연결 피어 추가 / 제거 |

`FINDNODE/v4`의 v4는 탐색 프로토콜 버전이다. UDP 탐색 메시지를 보냈다고 블록을 주고받는 피어 연결이 완료된 것은 아니다. 같은 노드와 여러 메시지를 교환하고 중복 소개도 받으므로 로그 줄 수는 노드 수와 다르다.

콘솔 입력이 어려워 다른 PowerShell에서 프로세스를 조회한 후 사용자가 종료했다. `go run`의 실행 파일이 Temp/go-build 아래에 있는 것은 정상이다. 다음 실행에는 같은 datadir를 사용한다.

## 로컬에 실제 저장된 양

실행 종료 후 파일 크기를 합산한 시점의 값이다. 디스크 할당 크기와는 다르다.

| 위치 | 크기 | 용도 |
|---|---:|---|
| node-data 전체 | 4,632,356바이트, 약 4.42MiB | 노드의 로컬 데이터 |
| geth/chaindata | 3,269,636바이트 | 체인 DB 및 초기화 데이터 |
| geth/nodes | 1,362,222바이트 | 노드 레코드와 탐색 이력 DB |
| geth/blobpool | 368바이트 | 사실상 초기 파일 수준 |
| keystore | 파일 없음 | 계정 키 저장 위치 |
| geth/nodekey | 64바이트 | P2P 노드 신원 키 |
| geth/jwtsecret | 66바이트 | Engine API 인증 비밀값 |

화면의 TRACE 로그 전체가 파일로 저장된 것은 아니다. chaindata의 숫자 이름 `.log` 파일은 DB의 내부 변경 기록이다. 이 크기만으로 저장 블록 높이는 판정하지 않았다.

노드 DB는 임시 Go 도구로 읽기 전용으로 열고 현재 키를 순회했다.

- `n:` 키에서 중복 제거한 노드 ID: **7,143개**.
- 완전한 `:v4` 노드 레코드 키: **4개**.
- 노드 레코드와 메타데이터 키 합계: **12,968개**.

7,143개 모두의 주소를 확보했거나 연결했다는 뜻은 아니다. 접촉 시각, 실패 횟수 등 메타데이터만 남은 ID도 포함한다. 과거 발견한 모든 노드의 누적 총수나 현재 온라인 노드 수도 아니다. 종료해도 저장 정보는 남지만 실제 연결은 다음 실행 때 다시 맺는다.

MiB는 1,048,576바이트, MB는 1,000,000바이트다. 둘 다 정확한 단위이고 기준만 다르며, 대략적인 용량 감각에서는 약 5% 차이다.

## 주석 영어와 다음 학습 방향

- `digest`: 받은 데이터를 처리한다. `feed`: 처리할 곳에 데이터를 전달한다.
- `fed as the transactions finish`: 트랜잭션이 끝나는 대로 receipt가 공급된다는 뜻. 쉼표 뒤 문구의 배치가 실행 순서는 아니다.
- `ready when the validator asks`: 요청하는 시점에 결과가 이미 준비되어 있다는 뜻. ready 자체가 계산이라는 뜻은 아니다.
- `With a tracer attached`: tracer가 연결된 조건. `it`은 단수 tracer를 받을 수 있고 복수 blooms라면 they가 필요하다.
- `Mutate ... according to ... specs`: 적용되는 명세에 따라 변경하라는 명령문 형태. specs는 specifications의 줄임말이다.
- receipt(영수증)와 recipe(요리법)는 다른 단어다.

스트레스 코드의 운영 수치를 깊게 파기보다, 실제 실행에서 관찰한 동작을 코드로 연결하기로 했다. 거래 실행은 `state_processor.go`와 `state_transition.go`, 피어 연결은 `p2p/dial.go`와 `p2p/server.go`를 중심으로 추적한다. 다음에는 RPC 유입 → TxPool 검증과 블록 실행 → Message 변환을 별도 경로로 구분해 읽는다.
