# 학습 작업일지: Geth 실행 준비와 Node의 수명

- 기록일: 2026-10-27
- 학습 범위: 실행 진입점, `makeFullNode()`, 서비스 등록과 시작, 데이터 디렉터리 잠금, 업그레이드 설정, `Node.Wait()`.
- 방식: 로컬 소스 확인과 질의응답. Geth 실행·빌드·테스트는 진행하지 않음.

## 실행 진입점부터 종료 대기까지

일반적인 노드 실행 기준으로 다음 순서를 확인했다. `geth version` 같은 하위 명령은 다른 실행 경로를 사용한다.

```text
패키지 변수 초기화 및 init()
  → main()
  → app.Run(os.Args): 명령줄 해석 및 사전 준비
  → geth(ctx)
      → prepare(ctx)
      → makeFullNode(ctx)
          → makeConfigNode(ctx)
              → loadBaseConfig(ctx)
              → node.New(&cfg.Node)
          → Ethereum 서비스와 API 등 등록
      → startNode(ctx, stack, false)
          → utils.StartNode(...)
          → Node.Start()
      → stack.Wait()
```

- `init()`은 Go가 `main()` 전에 자동 실행하는 특별한 함수다. Geth에서는 기본 실행 함수(`app.Action = geth`), 명령어, 옵션 등을 등록한다.
- `ctx *cli.Context`는 명령줄 옵션과 실행 정보를 읽는 객체다. `String`, `Bool`, `Uint64` 등으로 값을 읽고, `IsSet`으로 옵션이 명시적으로 설정됐는지 확인한다.
- `node.New()`의 `node`는 import한 패키지 이름이다. 생성된 `*node.Node`가 `stack`에 저장된다.
- 각 함수의 지역 변수 `stack`은 같은 Node 포인터를 전달받는다. 반환할 때마다 Node를 새로 만들거나 복제하지 않는다.
- 일반적인 Geth 실행은 Node 하나를 생성해 종료까지 사용한다. 싱글턴을 강제하는 구조는 아니므로 여러 개 생성할 수도 있지만, 데이터 디렉터리와 포트 등의 자원 충돌을 피해야 한다.
- `stack`은 여러 서비스와 통신 기능을 묶은 기반이라는 의미의 이름이며, 자료구조 스택을 뜻하지 않는다.

## makeFullNode가 준비하는 것

1. `makeConfigNode()`로 기본 Node와 설정을 받는다.
2. 명시된 업그레이드 적용 시점 변경 옵션을 설정에 반영한다.
3. `SetupMetrics()`와 OpenTelemetry로 관측 기능을 설정한다.
4. `RegisterEthService()`로 Ethereum 서비스를 생성·등록한다.
5. `geth/info`에 운영체제, CPU 아키텍처, Geth 버전, 지원 프로토콜 정보를 기록한다.
6. Filter API, 선택적인 GraphQL·EthStats, 동기화 보조 기능을 등록한다.
7. 개발 모드·비콘 라이트 클라이언트 모드·일반 모드에 따라 필요한 기능을 등록한다.
8. 구성을 마친 동일한 `stack`을 반환한다.

`makeFullNode()`는 주로 구성과 등록을 담당한다. 이후 `startNode()`가 Node와 등록된 서비스의 본격적인 시작을 진행한다. 다만 메트릭 수집처럼 구성 과정에서 시작되는 보조 고루틴도 있다.

### Ethereum 서비스 등록과 Start

```text
RegisterEthService(stack, cfg)
  → eth.New(stack, cfg)
      → Ethereum 객체와 구성 요소 생성
      → RegisterAPIs(eth.APIs())
      → RegisterProtocols(eth.Protocols())
      → RegisterLifecycle(eth)
```

`Node.Start()`에 도달했을 때 `n.lifecycles`에는 이미 `eth` 등의 객체가 등록돼 있다. 목록 복사는 서비스 객체 자체의 깊은 복제가 아니다. Node는 공통 P2P·RPC 기반을 연 뒤 등록된 서비스의 `Start()`를 순서대로 호출하고, 실패하면 이미 시작한 서비스들을 정리한다.

`Ethereum.Start()`는 피어 탐색 설정, 네트워크 처리 시작, 연결 관리, 체인 이벤트 구독, 로그 인덱서 실행 등을 수행한다. 생성·등록과 시작은 구분된다.

### 메트릭과 GaugeInfo

- `SetupMetrics(&cfg.Metrics)`는 상태 관찰용 기능이다. 비활성화돼 있으면 바로 반환하며, 블록체인 동작의 필수 조건은 아니다.
- 활성화 시 별도 고루틴에서 프로세스 상태를 3초 주기로 수집한다. 함수 전체가 3초마다 호출되는 것은 아니다.
- InfluxDB 전송과 HTTP 조회 기능은 설정에 따라 활성화된다. 전송 주기는 수집 주기와 별개다.
- `eth.Protocols()`는 지원하는 P2P 프로토콜 목록을 제공한다. `protos`에는 이름과 버전을 결합한 문자열들이 들어간다.
- `NewRegisteredGaugeInfo("geth/info", nil).Update(...)`는 실행 환경과 빌드 정보를 이름·값 형태로 기록한다. 프로토콜을 실행하는 코드가 아니다.

### Engine API

일반 모드의 마지막 `else`에서 `catalyst.Register(stack, eth)`로 Engine API를 등록한다. Ethereum 서비스 자체는 그 전에 이미 등록돼 있다.

- 합의 클라이언트는 이 API로 실행 클라이언트에 블록 검증, 체인 기준 갱신, 블록 생성 등을 요청한다.
- HTTP 기반 JSON-RPC에서는 URL 경로보다 요청 본문의 `method`로 작업을 구분한다.
- 같은 컴퓨터에서 합의·실행 클라이언트를 별도 프로세스로 실행하면 `localhost`로 연결할 수 있다. 서로 다른 컴퓨터라면 실행 클라이언트의 접근 가능한 주소를 사용한다.
- 개발 모드 조건은 실제로 `ctx.Bool(utils.DeveloperFlag.Name)`이며 `--dev`에 대응한다. 모의 비콘 서비스를 등록한다.

## 데이터 디렉터리와 파일 잠금

```go
instdir := filepath.Join(n.config.DataDir, n.config.name())
os.MkdirAll(instdir, 0700)
n.dirLock = flock.New(filepath.Join(instdir, "LOCK"))
locked, err := n.dirLock.TryLock()
```

- `DataDir`는 데이터 저장의 기본 디렉터리이고, `name()`은 인스턴스 디렉터리에 사용할 이름이다.
- 예를 들어 기본 경로가 `C:/ethereum`, 이름이 `geth`라면 인스턴스 디렉터리는 `C:/ethereum/geth`다.
- `filepath.Join()`은 운영체제에 맞게 경로 문자열을 결합한다. 파일을 생성하지 않는다.
- `flock.New()`는 `LOCK` 파일의 잠금을 관리할 객체를 만든다. `New`는 일반적인 생성 함수 이름이지 Go 특별 문법이 아니다.
- `TryLock()`은 파일을 열거나 생성해 운영체제 파일 잠금을 시도한다. 이미 다른 프로세스가 잠갔다면 기다리지 않고 실패를 알린다.
- 디렉터리 전체에 대한 모든 접근이 차단되는 것은 아니다. 같은 잠금 규칙을 따르는 Geth 프로세스끼리 중복 사용을 막는다.
- `geth.exe`를 두 번 실행해 같은 데이터 디렉터리를 사용하려 하면 두 번째 프로세스가 `ErrDatadirUsed`로 실패한다.

| 잠금 | 주로 보호하는 범위 | 해당 호출의 대기 방식 |
|---|---|---|
| `n.lock.Lock()` | 같은 프로세스의 고루틴 사이에서 Node의 공유 메모리 상태 | 획득할 때까지 대기 |
| `n.dirLock.TryLock()` | 프로세스 사이에서 데이터 디렉터리 중복 사용 | 즉시 성공·실패 반환 |

## 업그레이드 이름과 Override 설정

Osaka·Amsterdam은 실행 계층 업그레이드 이름이다. 개별 변경 제안인 EIP 여러 개를 하나의 업그레이드에 묶을 수 있다. 업그레이드마다 과거 블록 검증에 필요한 적용 시점을 관리하므로 기존 이름을 단순히 최신 이름으로 교체하지 않는다.

```go
if ctx.IsSet(utils.OverrideOsaka.Name) {
    v := ctx.Uint64(utils.OverrideOsaka.Name)
    cfg.Eth.OverrideOsaka = &v
}
```

- `IsSet()`은 Osaka라는 이름의 존재 여부가 아니라 사용자가 변경 옵션을 명시했는지 확인한다.
- `Uint64()`는 입력한 적용 시점을 정수로 읽는다. 값은 1970년 1월 1일 UTC부터 지난 초 수인 유닉스 타임스탬프다.
- `&v`는 해당 숫자를 담은 변수의 포인터를 설정에 저장한다.
- Override는 이미 구현된 규칙의 적용 시점을 로컬 설정에서 덮어쓴다. 미구현 기능을 만들어 주거나 메인넷 전체의 일정을 바꾸지는 않는다.
- 일반 메인넷 실행은 Override 없이 합의된 기본 일정을 따른다. 기준은 단순한 컴퓨터 현재 시간이 아니라 검증 대상 블록의 타임스탬프다.
- 같은 적용 시점을 지정하면 결과가 같지만, 시점을 바꾸면 특정 구간의 과거 블록에 적용하는 규칙도 달라질 수 있다.

## 마지막 학습 지점: Wait와 채널 대기

```go
func (n *Node) Wait() {
    <-n.stop
}
```

- `main()` → `geth()` → `stack.Wait()`는 일반 함수 호출이므로 같은 메인 고루틴에서 실행된다. 함수 호출만으로 새 고루틴이 생기지 않는다.
- `n.stop`은 `make(chan struct{})`로 생성한 종료 알림용 채널이다.
- `<-n.stop`은 채널 수신이다. 값이 없고 열려 있으면 호출한 고루틴이 대기한다. 반복문으로 계속 확인하는 방식이 아니다.
- 메인 고루틴이 대기하는 동안 네트워크·동기화 등 다른 고루틴은 계속 동작한다.
- 종료 과정의 `close(n.stop)`이 채널을 닫으면 수신 대기가 풀리고 `Wait()`가 반환한다.
- 이 대기는 Mutex 잠금 때문에 발생하는 것이 아니다. 채널 수신 규칙과 Go 런타임이 대기를 처리한다.
