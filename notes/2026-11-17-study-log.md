# 2026-11-17 학습 작업일지

관찰일·기록일: 2026-11-17 (Asia/Seoul). 토스 코인지갑을 계기로 진행한 대화 학습을 기록한다. 아래 상태는 에이전트의 설명·자료 조사와 사용자 발언을 근거로 하며, 독립 수행이나 법률 판단을 의미하지 않는다.

## 1. 오늘의 범위와 실제 수행

- 토스 코인지갑 출시 기사를 출발점으로 수탁·비수탁, 개인키의 보관과 사용 권한, MPC, WaaS, 복구·export의 관계를 질문하고 설명을 함께 검토했다.
- 에이전트가 토스 공식 팀 인터뷰, 금융위·FIU 안내, 거래소 출금 정책 및 지갑 인프라 문서를 조회했다. 사용자는 기사 문구와 설명 사이의 모순 가능성을 제기하고, 가설의 근거를 재확인했다.
- 지갑 간 온체인 전송과 중앙화 거래소의 출금 허용 정책, 네트워크 가스비와 거래소의 정액 출금료를 구분하는 설명을 다뤘다. VASP 신고의 목적, ISMS, 매매·교환 중개 사례도 다뤘다.
- 보조 개념으로 EIP-1559의 기본료·팁·최대 가스 단가와 CROPS의 의미를 설명했다. 이 항목들은 설명 접함 상태이며, 사용자 재설명은 확인하지 않았다.
- Geth·Lighthouse 소스를 새로 추적하거나 수정하지 않았다. 노드 실행, 지갑 생성·연결, 개인키 조회·내보내기, 서명·송금, 스마트계약 배포, 테스트는 수행하지 않았다.

## 3. 이전 혼동과 현재 상태

- 에이전트가 ‘회사가 혼자 송금할 수 있는가’를 중심으로 설명하면서 법적·운영상 승인과 암호학적 권한, 공동 통제를 충분히 분리하지 못했다. 이후 사용자 측 필수 요소, 업체 간 조합, 복구·관리자 권한과 탈출 경로를 함께 확인해야 한다고 보완했다. 반복 질문에는 설명의 부정확성도 영향을 줬다.
- 기사 속 ‘토스가 개인키를 보호한다’는 문구만으로 사용 가능한 전체 키 보관, 암호화된 백업, MPC, 패스키 중 하나를 특정할 수 없다. 특정 방식을 우선 후보로 언급했지만 검증된 설계로 기록하지 않는다.
- 토스의 2026-09-21 공식 팀 인터뷰는 사용자에게 키의 100% 통제권을 부여하고 키 추출·외부 지갑 사용을 가능하게 설계했다고 설명한다. 이는 회사의 설계 설명이며 독립 보안 검증 결과가 아니다. export 지원만으로 회사의 기존 서명 권한 부재가 입증되는 것도 아니다.
- 2026-11-16 주요 보도는 ‘이번 주 일반 대상 출시 예정’이다. 관찰 당일 오전 조사에서는 정확한 오픈 날짜와 전 이용자 개방 완료를 확인하지 못했다. 일부 재전달 기사의 ‘출시했다’ 표현만으로 완료를 판정하지 않았다.
- 업비트에 토스가 지원 개인지갑으로 명시되지 않았다고 곧바로 모든 출금을 불가로 단정할 수는 없다. 조회한 안내에는 100만원 미만 주소의 별도 심사 절차가 있었지만, 토스 주소가 실제 승인된 사례는 확인하지 않았다. 당시 안내의 금액 기준·허용 목록은 영구적인 법률 기준으로 일반화하지 않는다.
- 네트워크 가스비와 거래소의 정액 출금료는 다르다. 메인넷 비용이 항상 높다는 초기 인상을 실시간 표본 조회로 보정했다. 표본은 토스의 실제 송금 견적이나 거래소의 실제 원가가 아니며, 수수료 차액 전부를 순이익으로 단정하지 않는다. USDT와 USDC의 서로 다른 출금료도 구분했다.
- VASP는 수탁 전용 자격이나 기술 안전성 인증이 아니다. 비수탁 지갑의 신고 제외 가능성과 매매·교환·중개 등 별도 영업의 신고 여부를 구분했다. 11월 16일 보도는 토스의 VASP 준비를 언급했으며, 토스의 신고 수리 완료·개별 신고 제외 판단은 확인하지 않았다.
- ISMS, EIP-1559, CROPS는 설명을 제공한 상태다. ISMS는 무사고 보증이 아니고, EIP-1559는 가스비를 항상 낮추는 규격이 아니며, CROPS의 프라이버시 원칙이 일반 송금 내역의 비공개를 의미하지 않음을 구분했다.

## 5. 다음에 확인할 작은 과제

아래는 후속 제안이며 아직 수행하지 않았다. 실제 자산이나 실사용 개인키는 사용하지 않는다.

1. 사용자·회사·복구업체의 권한표 작성. 통과 기준: 2-of-3과 사용자 필수 구조에서 가능한 서명 조합을 빠짐없이 나열하고, 평상시 송금·분실 복구·export 후 통제를 구분한다. 기술적 분류와 법적 판단의 경계도 표시한다.
2. 개발용 키의 서명·검증 경로를 Geth 소스에서 짧게 추적. 통과 기준: 키 보호·복호화, 서명 생성, 서명 검증의 역할을 나누고 실제 호출부와 구현을 제시한다. 이번 세션에서는 관련 심볼을 새로 검증하지 않았다.
3. 가상의 USDT 출금 견적을 같은 조건으로 비교. 통과 기준: 자산·네트워크·조회 시각·가스 사용량·유효 단가·환산값을 명시하고, 정액 거래소 출금료와 구분한다. EIP-1559 최대 단가를 실제 지불액으로 오해하지 않는다.

## 6. 취업 관점

- 월렛·블록체인 백엔드의 인증과 서명 권한 분리, 키 수명주기, 복구·이관 설계, 네트워크 선택, 출금 정책·비용 안내 요구사항과 관련된다. 사업 설명에서 구현 가설과 검증된 사실을 분리하는 연습이기도 하다.
- 사용자가 기사 문구와 실제 정책 수치를 대조해 모호함을 드러낸 사례는 관찰했다. 다만 키 관리 구현, 암호 프로토콜 분석, 보안 검증, 거래소 연동 개발, 장애 대응·운영 경험은 이번 대화로 입증되지 않는다.
- Geth 학습과 연결할 다음 증거는 실제 서명·검증 경로의 독립 소스 추적이나 개발용 키를 이용한 작은 테스트다. 목표 직무가 월렛 개발자로 확정됐다는 뜻은 아니다.

## 7. 탐색 방식과 범위

- 중심은 제품 설명을 기술·정책 개념으로 나누는 큰 구조 파악과 개념 정리였다. 원문 문구 → 가능한 설계 → 공식 자료의 추가 단서를 오가며 검토했다.
- MPC의 임계치 조합, 암호화 백업, 패스키 기반 복구, WaaS와 수탁 모델의 구분까지 설명했다. MPC 알고리즘·TEE 신뢰 모델·스마트계약 관리자 권한의 실제 구현은 분석하지 않았다.
- EIP-1559의 설명은 기본료·팁·상한과 실제 비용의 관계까지이며, Geth의 수수료 계산 구현이나 트랜잭션 풀 정책 추적은 하지 않았다.
- 토스 학습과 직접 관련 없는 투자 행동이나 별도 해킹 사건의 피해액 비교는 이번 기록 범위에 넣지 않았다.

## 8. 질문·협업 방식

- 관찰: ‘개인키를 보호한다’와 ‘직접 보관한다’가 같은 말인지 거듭 확인하고, 회사가 키를 갖는데 사용자 허가가 필요하다는 설명의 모순 가능성을 지적했다. 용어가 실제 권한 구조를 충분히 설명하는지 확인하려는 접근으로 해석할 수 있다. 요구사항·보안 경계 검토에 도움이 될 가능성은 있으나 실제 업무 성과는 미확인이다.
- 관찰: 비수탁 인프라와 VASP 준비가 어떻게 연결되는지 묻고, ‘중개’의 구체적 사례를 요청했다. 추상적인 분류를 서비스 동작으로 바꾸어 확인하려는 행동이었다. 법률 적용을 독립 판단했다는 뜻은 아니다.
- 관찰: 업비트의 USDT 출금료 표시를 근거로 앞선 USDC 중심 답변을 정정하게 했다. 자산명·비교 조건의 불일치를 드러낸 사례다. 그 이상의 독립 원가 분석은 확인하지 않았다.

# 추가 세션: Geth 피어 연결과 트랜잭션 실행 흐름

관찰일·기록일: 2026-11-17 (Asia/Seoul). 앞선 지갑 세션을 보존하고 추가한다. 앞부분의 ‘Geth 소스를 새로 추적하지 않았다’는 문장은 앞선 세션에만 해당한다. 이번 세션에서는 에이전트가 로컬 소스를 조회했다.

## 1. 오늘의 범위와 실제 수행

- discovery 후보 공급부터 `readNodes`의 채널 전송, dial scheduler의 수신, TCP 연결, 핸드셰이크, Peer 보관까지 호출 경로를 대화로 추적했다. 소스 검색·발췌는 에이전트가 수행했다.
- 사용자는 피어 등록까지의 대략적인 흐름은 어제 학습했다고 말했다. 이는 사용자 보고로 남기며, 오늘 독립 재설명으로 검증한 것은 아니다.
- RLPx 인증 메시지 생성에서 장기 키, 임시 키, nonce, 공유 비밀값의 역할을 짧게 확인했다. 암호 프로토콜 전체의 보안 성질이나 수학적 검증은 분석하지 않았다.
- 사용자가 제공한 멀티체인 백엔드 채용 공고와 현재 공부의 연결을 검토하고, 입금 감지·DB 저장·중단 후 복구 실습을 제안했다. 해당 공고의 회사·최신 게시 여부는 조사하지 않았다.
- `--dev`의 P2P 비활성화와 내부 SimulatedBeacon, 실행·합의 계층 역할, 실행 페이로드, 풀에서 트랜잭션을 선별·적용하는 경로를 설명했다.
- 노드 실행, 코드 구현·수정, 송금, DB 구축, 테스트는 하지 않았다. 예시와 후속 실습 제안은 실행 결과가 아니다.

## 3. 이전 혼동과 현재 상태

- FairMix는 bucket 자체나 인터페이스가 아니라 여러 후보 공급원을 섞는 구조체이며, dial scheduler에는 enode.Iterator로 전달된다고 설명했다. discovery 내부 후보 선택 알고리즘까지 분석한 것은 아니다.
- startStaticDials와 startDial을 구분했다. 전자는 고정 노드 연결 작업을 시작하는 경로이며, discovery 후보도 별도 수신 분기에서 startDial을 호출한다.
- SetupConn은 TCP 접속 자체가 아니라 성공한 연결의 핸드셰이크·피어 등록 시도다. 외부 연결 경로에서는 함수 값으로 전달되어 d.setupFunc로 호출되므로 이름으로 직접 호출하는 위치만 찾으면 놓칠 수 있다.
- fd는 여기서 정수 파일 디스크립터가 아니라 net.Conn 변수다. Peer에 직접 fd 필드가 있는 것이 아니라 Peer.rw가 conn을 참조하고 conn.fd가 연결을 보관한다.
- RLPx 서명에 ‘노드의 장기 개인키와 제공받은 해시’를 직접 넣는다는 가설을 정정했다. makeAuthMsg는 장기 키 ECDH 공유값과 nonce를 XOR한 32바이트 값에 임시 개인키로 서명한다. 사용자 독립 재검증은 하지 않았다.
- ‘모든 트랜잭션을 EVM으로 실행’이라는 에이전트 표현을 보완했다. 트랜잭션 실행은 원장 상태에 요청을 적용하는 넓은 의미이고, 바이트코드 실행은 그중 코드가 실행되는 경우다. 일반 ETH 전송도 잔액·nonce·가스 처리를 한다. 주소 종류만으로 코드 실행 여부를 영구적으로 단정하지 않는다.
- ‘블록 후보’는 별도 저장통이 아니라 생성 중이거나 아직 정식 체인에 채택되지 않은 블록을 가리킨 설명이었다. 사용자가 용어의 필요성을 질문해 생성과 체인 채택의 차이로 풀어 설명했다.
- 트랜잭션 목록은 순서가 있으며 앞 거래의 상태 변경이 뒤 거래의 유효성·결과에 영향을 줄 수 있다. 수수료를 생략한 A→B→C 예시는 설명용이며 실행한 실험이 아니다.

## 4. 실무 역량 증거

- 사용자 독립 구현·실행·운영 산출물은 이번 세션에 없다. 재현 가능한 송금·인덱싱·복구 결과도 없다.
- 에이전트가 rg와 소스 발췌로 호출부·구현을 대조하고 일지를 작성했다. 이를 사용자의 독립 코드 탐색·실행 능력으로 인정하지 않는다.
- 최소 소스 참조:
  - `go-ethereum/p2p/server.go`: setupDialScheduler, SetupConn, setupConn, launchPeer.
  - `go-ethereum/p2p/dial.go`: readNodes, loop, startDial, dialTask.dial, tcpDialer.Dial.
  - `go-ethereum/p2p/rlpx/rlpx.go`: makeAuthMsg, handleAuthMsg.
  - `go-ethereum/eth/catalyst/simulated_beacon.go`: sealBlock.
  - `go-ethereum/eth/api_backend.go`: SendTx → txPool.Add.
  - `go-ethereum/miner/worker.go`: fillTransactions → commitTransactions → commitTransaction → applyTransaction.
  - `go-ethereum/core/state_processor.go`: ApplyTransaction. `core/state_transition.go`: executeCall / executeCreate.

## 5. 다음에 확인할 작은 과제와 통과 기준

1. 로컬 --dev 체인을 실행하고 JSON-RPC로 블록·잔액을 조회한다. 통과 기준: 사용자가 명령·응답·체인 식별 정보를 남기고 일반 네트워크와 dev 모드의 차이를 설명한다. 빌드·환경 구성은 아직 수행하지 않았다.
2. 테스트 ETH 전송 후 트랜잭션과 영수증을 조회한다. 통과 기준: 트랜잭션 해시, 포함 블록, 실행 상태, 잔액 변화를 직접 확인하고 제출 응답과 블록 포함의 차이를 설명한다.
3. 특정 주소의 일반 ETH 입금을 저장하는 최소 수집기를 만든다. 통과 기준: 직접 만든 테스트 전송 감지, 재시작 중복 방지, 수집 중단 중 놓친 블록 복구를 확인한다. 컨트랙트 내부 ETH 이동·토큰·reorg 처리는 후속 범위로 둔다.

## 6. 취업 관점

- 제공된 공고의 코어 코드 탐색 우대사항과 현재 Geth 학습이 연결된다. 다만 입출금·스테이킹·온체인 데이터 정합성 백엔드 업무의 수행 증거를 대신하지 않는다.
- 입금 수집 실습은 JSON-RPC 연동, 저장, 복구, 데이터 검증 역량으로 이어질 수 있는 제안이다. 아직 기여나 완성된 포트폴리오로 기록하지 않는다.
- 멀티체인 경험, PoS 운영, 밸리데이터 구축, 대용량 파이프라인, 실제 동료 협업은 이번 대화에서 미확인이다. 다른 경력·언어 역량을 이 질문들만으로 추정하지 않는다. 목표 직무가 최종 확정됐다고 기록하지 않는다.

## 7. 탐색 방식과 범위

- 중심은 큰 호출 흐름을 데이터·객체·실행 시점과 연결하는 탐색이었다. 채널 변수 대입, 함수 값 간접 호출, 연결 객체 보관은 세부 확인했으나 네트워크 스케줄링 전체나 암호 알고리즘을 깊이 분석한 세션은 아니다.
- 후반에는 피어 등록에서 실무 체험으로 관심이 이동했다. RPC 접수·풀 보관·블록 구성·상태 적용의 경계를 소스로 확인했으나 EVM 명령어 해석기, 풀 정책 전체, 상태 트라이 구현까지 내려가지 않았다.
- 일반 PoS는 별도 합의 클라이언트가 체인 선택을 전달하고, dev 모드는 내부 SimulatedBeacon이 간소화한 역할을 수행한다. 개발 모드 결과를 실제 다중 검증인 합의 실험으로 취급하지 않는다.

## 8. 질문·협업 방식

- 관찰: “nodesIn으로 전달했는데 왜 nodesCh가 받는가”, “reference에는 listenLoop 말고 안 보인다”라고 실제 변수·호출 위치와 설명의 연결을 확인했다. 참조 관계나 간접 호출을 명시해야 이해를 이어가는 접근으로 해석할 수 있다. 코드 전달·리뷰에서 연결 고리 누락을 드러내는 데 도움이 될 가능성이 있으나 실제 팀 성과는 미검증이다.
- 관찰: payload의 사전적 의미까지 요청하며 “이름의 뜻을 이해하고 나야 나중에 안 까먹고 연결될 것”이라고 학습 방식을 직접 설명했다. 용어와 역할의 연결을 선호한 이번 맥락의 증거이며 기억력이나 고정 성격 판단으로 확대하지 않는다.
- 관찰: ‘EVM으로 실행’, ‘블록 후보’, ‘일반 트랜잭션 실행’이라는 표현에 의문을 제기했다. 이로 인해 에이전트의 과도한 축약을 보완했다. 반복 질문의 원인에 앞선 설명의 부정확성도 포함될 수 있다.
- 관찰: “실제 실무에서 해볼 만한 것들을 체험”하고 싶다고 다음 학습 방향을 명시했다. 실습 지향 의사 표현이며 실행 완수나 일정 관리 능력이 입증된 것은 아니다.
- 2026-11-07·11-09 누적 기록의 이름·역할·실행 시점 확인과 유사한 질문이 이번에도 관찰됐다. 동료와의 코드 리뷰·역할 분담·피드백 수용은 별도의 실제 증거가 필요하다. 질문 수·말투·속도로 생산성이나 협업 비용을 평가하지 않는다.
