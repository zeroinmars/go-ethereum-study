## 3. 이전 혼동과 현재 상태

- endpoint를 URL의 고정된 구간으로 이해하려는 질문이 있었다. 에이전트가 처음에는 서버/클라이언트 관점으로 잘못 구분했고, 이후 문맥에 따라 접속 지점을 가리키는 말이라고 정정했다. 이 코드의 endpoint는 host·port 문자열이라는 관계는 사용자가 재진술했다.
- `listener.Addr()`가 외부 사용자 주소인지, 공인 IP인지 질문했다. 서버가 바인딩한 로컬 주소를 조회한다고 설명했다. 반복 질문에는 에이전트가 기본 흐름보다 예외를 먼저 강조한 설명도 영향을 줬을 수 있으며, 사용자 능력의 결함으로 해석하지 않는다.
- 내부 RPC 클라이언트가 요청을 받는 것인지 질문했다. 받는 쪽은 `rpc.Server`이며 `/rpc` 경로가 실행할 메서드를 고르는 것은 아니라고 설명했다. 이후 올바른 역할 구분을 독립적으로 재설명했는지는 미확인이다.
- HTTP 연결 전환 요청과 이후 WebSocket JSON-RPC 메시지를 구분해 설명했다. WebSocket에서는 같은 연결을 유지하며 메시지마다 바깥 `h.ServeHTTP`를 다시 거치지 않고, 일반 HTTP RPC에서는 각 요청이 `ServeHTTP`를 거친다는 설명을 접했다. 실행으로 검증하지 않았다.

## 4. 실무 역량 증거

- 사용자 산출물: 대화에서 주소 설정과 요청 위임 흐름을 재진술한 발언. 재현 가능한 실행·구현 산출물은 없다.
- 에이전트 수행: `rg`, `Get-Content`로 관련 로컬 소스를 확인하고 설명 및 이 일지를 작성했다. 사용자 독립 코드 탐색이나 수행 증거로 계산하지 않는다.
- 실제 장애 재현, RPC 요청·응답, 테스트 결과, 운영 성과는 이번 세션에서 확인하지 않았다.

## 5. 다음에 확인할 작은 과제

1. `host/port → endpoint → net.Listen → listener.Addr()`를 도움 없이 설명한다. 통과 기준: 설정 시점과 바인딩 시점을 구분하고, 포트 0일 때 두 주소가 달라지는 이유를 설명한다.
2. WebSocket 연결 요청부터 `eth_blockNumber` 응답까지 흐름을 그린다. 통과 기준: 외부 클라이언트·HTTP 서버·WS 핸들러·RPC 서버를 구분하고, 같은 연결 유지 및 path와 method의 차이를 설명한다.
3. `wsHandler.Store`와 `Load`의 호출부를 직접 찾는다. 통과 기준: 생성·포인터 저장·포인터 읽기·실제 핸들러 실행을 구분하고 해당 소스 위치를 제시한다.

모두 제안 단계이며 완료 처리하지 않았다.
