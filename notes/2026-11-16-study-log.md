# 2026-11-16 학습 작업일지

## 1. 오늘의 범위와 실제 수행

- Geth P2P 시작 흐름에서 `Server.Start()`의 `setupDialScheduler()`와 `srv.run()`을 출발점으로, 후보 탐색 → TCP 연결 → 핸드셰이크 → 피어 등록 → 피어별 통신의 큰 구조를 함께 살폈다.
- 에이전트가 로컬 소스의 호출부와 구현을 조회하고 설명했다. 사용자는 제시한 코드에 대해 질문하고 관계를 자기 말로 연결했다. 사용자의 독립 소스 탐색·구현·실행은 이번 대화에서 확인하지 않았다.
- `matchProtocols`, `protoRW`, `Peer.running`, 피어 이벤트 구독, `Peer.run()`의 역할을 설명했다. 노드 실행이나 Geth·Lighthouse 소스 수정은 하지 않았다.
- 일반 P2P 서버 경로를 다뤘으며 개발 모드·부하 테스트 경로는 분석하지 않았다.

## 3. 이전 혼동과 현재 상태

- 에이전트가 처음 다음 분석 대상으로 `SetupConn()`을 제안하면서 호출 경로를 생략했다. 사용자가 “왜 갑자기 SetupConn이야?”, “그걸 어디서 실행하는데?”라고 지적했다. 이후 스케줄러 → `startDial` → 작업 실행 → TCP 연결 성공 → `setupFunc` 호출 경로를 보완했다. 혼동에 설명의 생략도 영향을 줬으며 사용자 능력 부족으로 해석하지 않는다.
- `checkpointAddPeer`는 등록 완료 알림이 아니라 등록 요청이며, `peers[c.node.ID()] = p`가 목록 등록임을 설명했다. 사용자 재설명이나 실행 검증은 아직 없다.
- `peerFeed.Send()`의 수신자는 상대 블록체인 피어가 아니라 등록된 채널이다. `RemovePeer()`의 종료 대기와 RPC 피어 이벤트 전달을 실제 사용 예로 확인했다. `runPeer()`의 두 Send 사이에서 `p.run()` 반환을 기다린다는 점을 설명했다.
- `peers`는 전역변수가 아니라 서버 관리 루프에 소유된 지역 맵이다. 서버가 실행되는 동안 유지되고, 현재 등록된 피어 목록의 기준이 된다고 범위를 한정했다. 모든 피어 정보가 맵 자체에만 저장되는 것은 아니다.
- 여기서의 프로토콜 핸드셰이크는 devp2p capability 교환이다. `eth` 프로토콜 자체의 후속 초기 교환까지 전부 분석한 것은 아니다.
- 위 항목은 설명을 제공한 상태이며, 모두 해결·숙달했다고 판정하지 않는다.

## 4. 실무 역량 증거

- 사용자가 작성한 코드, 실행 명령, 테스트 결과, 장애 재현 등 독립 수행 산출물은 이번 대화에 없다.
- 확인 가능한 증거는 사용자 발언과 에이전트의 로컬 소스 조회다. 소스 조회·경로 정리·설명·이 일지 작성은 에이전트가 수행했다.
- 최소 참조: `p2p/server.go`의 `setupDialScheduler`, `setupConn`, `Server.run`, `launchPeer`, `runPeer`, `SubscribeEvents`, `RemovePeer`; `p2p/dial.go`의 `newDialScheduler`, `dialScheduler.loop`, `startDial`, `dialTask.dial`; `p2p/peer.go`의 `newPeer`, `matchProtocols`, `protoRW`, `Peer.run`, `startProtocols`; `node/api.go`의 `PeerEvents`.
- 검증 방법: 위 심볼의 함수 전달·호출, 채널 송수신, 맵 대입문을 소스에서 확인했다. 실행 시 동작이나 패킷 흐름은 검증하지 않았다.

## 5. 다음에 확인할 작은 과제

1. 연결부터 등록까지 함수와 채널을 짧게 그려 보기. 통과 기준: TCP 연결 성공, `SetupConn`, 등록 요청 채널, 최종 검사, 맵 대입을 구분한다.
2. `Peer.run()`과 `readLoop()`에서 메시지 하나가 프로토콜 처리 쪽으로 전달되는 경로를 찾아 보기. 통과 기준: 읽기·분배·프로토콜 처리를 구분하고 근거 코드를 제시한다. 아직 직접 수행하지 않았다.
3. `runPeer()`의 두 이벤트 사이에 실행되는 코드를 설명해 보기. 통과 기준: 일반 함수 호출이 반환해야 다음 줄로 진행된다는 점과, 내부 구독 채널을 통한 알림임을 설명한다.

## 6. 취업 관점

- 네트워크 연결 수명주기, 비동기 작업, 이벤트 구독, 공유 상태의 소유 구조를 읽는 연습으로 클라이언트 개발·블록체인 백엔드·노드 인프라 분석의 기초와 관련된다. 목표 직무가 확정됐다는 뜻은 아니다.
- 이번 근거는 설명을 받으며 구조를 연결한 수준이다. 독립 코드 추적, 구현·테스트, 장애 분석, 운영 역량은 아직 확인하지 않았다.

## 7. 탐색 방식과 범위

- 중심은 세부 알고리즘보다 큰 구조 파악과 개념 구분이었다. 사용자가 “일단 크게크게 넘어가야될거같아”, “loop안에 너무 많은데 뭘 봐야돼?”라고 범위 조절을 요청했다.
- 호출 관계, 객체 필드, 채널, 맵 대입까지 확인했다. 스케줄러의 타이머·재시도 정책 전체, 암호화 구현, TCP 바이트 처리, 개별 eth 메시지 처리까지 깊게 분석하지 않았다.

## 8. 질문·협업 방식

- 관찰: 함수 값이 필드에 저장된다는 설명을 받아들인 뒤 실제 실행 위치를 반복해서 요청했다. 추상 설명을 호출 지점에 연결하려는 접근으로 해석할 수 있다. 코드 변경의 실제 효과를 확인하는 업무에 도움이 될 가능성이 있지만, 독립 디버깅 성과는 별도 확인이 필요하다.
- 관찰: 이벤트 수신자를 외부 피어로 이해한 상태에서 “왜 종료 관련 이벤트도 각 피어들에게 보내는거야?”라고 모순을 제기했다. 전달 대상의 모호함을 드러낸 사례다. 설명을 듣고 이후에는 구독 등록 시점을 Unity 이벤트에 비유해 확인했다.
- 관찰: 넓은 흐름을 먼저 요청하면서도 등록 대입 위치와 지역변수 수명은 따로 확인했다. 큰 구조와 특정 의미를 오가며 이해를 맞춘 세션이다. 질문 수로 생산성·소통 비용을 평가하지 않는다.
- 한계: 에이전트와의 질의응답만 관찰했다. 동료 코드 리뷰, 역할 분담, 일정 조율, 문서 전달 능력은 입증되지 않았다. 위 행동의 반복 여부도 다른 날짜 기록과 대조하지 않았다.
