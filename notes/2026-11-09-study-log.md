## 3. 이전 혼동과 현재 상태

- `server`의 “Currently running” 주석을 실행 중에만 객체가 할당된다는 뜻으로 해석할 가능성을 제기했다. `New`의 객체 생성과 `Start`의 실제 실행이 별도라는 설명을 접했다. 이후 `httpServer`와 `http.Server`의 경계는 자기 말로 연결했다.
- `startRPC`에 P2P 시작도 포함된다는 표현은 `openEndpoints`가 두 경로를 묶는다는 설명으로 정정했다. 정정 후 독립 재설명은 미확인이다.
- `rpc.NewServer()`가 기존 객체를 가져오는지, 네트워크를 실행하는지 질문했다. 새 객체 생성·API 등록과 `net.Listen`·`Serve` 실행을 구분해 설명했다. `Serve`의 지속 실행과 고루틴 관계는 부분 이해가 관찰됐다.
- HTTP가 WS를 포함하는 상위 개념인지 질문했다. 일반적인 HTTP Upgrade를 통한 WS 연결 시작과 Geth 객체의 공통 관리 역할을 설명했다. 프로토콜 전체를 분석한 것은 아니다.
- `jwtSecret`은 JWT 자체가 아니라 서명·검증용 공유 비밀 키라는 설명을 접했다. 사용자 OAuth 흐름과 Engine API 통신의 인증 방식 차이를 직접 검증하지는 않았다.
- 에이전트가 제시한 `Serve` 반복문은 개념적 의사 코드다. 실제 표준 라이브러리 구현을 함께 추적한 결과로 간주하지 않는다.

### 3. 혼동과 정정

- `http.Handler`를 구조체로 이해한 표현이 있었다. 인터페이스라는 설명 후 사용자가 인터페이스 충족 관계를 직접 연결했다.
- `http.HandlerFunc(...)`를 함수 호출로 읽었다. `type HandlerFunc func(...)`라는 선언과 타입 변환 문법, 그 타입의 `ServeHTTP` 메서드를 함께 확인했다. 본문 안에 메서드가 들어가는 구조가 아니라 함수 타입에 메서드가 정의된 구조임을 설명했다.
- Handler 재할당을 이전 객체 삭제로 이해할 가능성을 질문했다. 새 처리기가 이전 처리기를 `next` 또는 클로저로 참조하는 감싸기 구조를 설명했다. 메모리 수명이나 GC 동작은 검증하지 않았다.
- 사용자는 `rpcHandler.Handler`의 실제 값이 `HandlerFunc`라고 일반화했다. CORS 처리기는 함수 타입이지만 VHost 등은 구조체 구현체이며, 전체 스택에는 바깥 처리기가 반환된다는 정정 설명을 접했다. 이 예외까지 포함한 독립 재설명은 미확인이다.
- CORS·JWT·gzip 등 모두를 검사로 묶지 않도록, 검사와 응답 가공의 차이를 설명했다. 미들웨어마다 다음 처리기를 호출하거나 중단할 수 있음을 설명했다.

### 4. 실무 증거와 도움 범위

에이전트가 로컬 소스에서 `HandlerFunc.ServeHTTP`의 본문이 `f(w,r)`임을 확인하고 CORS의 익명 함수 반환·실행과 연결했다. 이는 에이전트의 소스 확인이며 사용자 실행 증거가 아니다. HTTP 요청, 실패 응답, 미들웨어 호출 순서 로그를 실제로 검증한 산출물은 없다. Geth·Lighthouse 소스는 수정하거나 실행하지 않았다.

### 5. 다음 작은 확인 과제

1. 도움 없이 Handler 구성 시점과 요청 처리 시점을 두 단계로 그리기. 통과 기준: `NewHTTPHandlerStack` 호출, 반환값 저장, `ServeHTTP` 호출을 구분하고 CORS와 구조체 처리기의 실제 타입 차이를 설명한다.
2. 최소 HTTP 예제에 로그를 남기는 미들웨어 하나 작성하기. 통과 기준: 구성 로그는 시작 시, 요청 로그는 요청마다 찍히는 것을 직접 확인하고 다음 처리기 호출 전후를 설명한다. 아직 수행하지 않은 제안이다.

### 6. 취업 관점

웹 백엔드의 인터페이스·미들웨어 이해와 노드 RPC 요청 경로 분석에 연결되는 기초다. 사용자는 Geth 조회 결과를 회사 백엔드가 받아 사용자에게 제공하는 구조도 자기 말로 연결했다. 실제 서비스 구현·인덱싱·운영 역량은 미확인이다. 직무 후보와 준비 기간에 관한 대화는 계획용 추정이며 채용 가능 수준을 검증한 결과가 아니다.

### 7. 탐색 방식과 깊이

요청 흐름을 이해하다 함수 타입·메서드·인터페이스 문법으로 내려간 뒤, 다시 미들웨어의 실제 역할로 돌아왔다. 표준 라이브러리의 짧은 어댑터 메서드와 CORS 클로저까지 확인했지만 HTTP 수신 루프 전체나 보안 처리의 모든 분기를 분석하지 않았다.

### 8. 질문·협업 관찰

“그 달려 있는 실제 코드는 어디 있는데?”, “문법적으로는 얼핏 이해 … 로직적으로는 … 뭘 하는 거야?”라고 선언·구현 근거와 업무 목적을 각각 요구했다. 이전의 이름·실제 역할 확인에 이어 문법 설명만으로 끝내지 않고 실행 흐름으로 연결하려는 행동이 관찰됐다. 프레임워크 미들웨어라는 기존 개념과 연결한 점도 관찰됐다. 코드 리뷰에서 추상화의 실제 효과를 확인하는 데 도움이 될 가능성은 있지만, 독립 분석 속도·생산성·팀 협업 효과는 별도 관찰 대상이다.
