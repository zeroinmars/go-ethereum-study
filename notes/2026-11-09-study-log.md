# 2026-11-09 작업일지

## 1. 오늘의 범위와 실제 수행

Geth의 P2P 시작과 RPC 시작을 구분하고, RPC 서버 객체 생성·설정·요청 수신·메서드 호출의 관계를 대화로 살펴봤다. 사용자는 코드 조각을 제시하고 자신의 해석을 확인했다. 에이전트가 로컬 소스의 호출부와 구현을 검색·열람하고 설명했다. 사용자 직접 구현·빌드·테스트·노드 실행은 관찰되지 않았다. 대화의 독립 HTTP 서버 예제는 설명용이며 실행 결과가 아니다.

주요 참조:
- `go-ethereum/node/node.go`: `New`, `openEndpoints`, `startRPC`, `wsServerForPort`
- `go-ethereum/node/rpcstack.go`: `httpServer`, `rpcHandler`, `enableRPC`, `start`, `ServeHTTP`, `isWebsocket`, `checkPath`
- `go-ethereum/rpc/server.go`, `service.go`, `handler.go`: `NewServer`, API 등록 및 호출 경로

## 3. 이전 혼동과 현재 상태

- `server`의 “Currently running” 주석을 실행 중에만 객체가 할당된다는 뜻으로 해석할 가능성을 제기했다. `New`의 객체 생성과 `Start`의 실제 실행이 별도라는 설명을 접했다. 이후 `httpServer`와 `http.Server`의 경계는 자기 말로 연결했다.
- `startRPC`에 P2P 시작도 포함된다는 표현은 `openEndpoints`가 두 경로를 묶는다는 설명으로 정정했다. 정정 후 독립 재설명은 미확인이다.
- `rpc.NewServer()`가 기존 객체를 가져오는지, 네트워크를 실행하는지 질문했다. 새 객체 생성·API 등록과 `net.Listen`·`Serve` 실행을 구분해 설명했다. `Serve`의 지속 실행과 고루틴 관계는 부분 이해가 관찰됐다.
- HTTP가 WS를 포함하는 상위 개념인지 질문했다. 일반적인 HTTP Upgrade를 통한 WS 연결 시작과 Geth 객체의 공통 관리 역할을 설명했다. 프로토콜 전체를 분석한 것은 아니다.
- `jwtSecret`은 JWT 자체가 아니라 서명·검증용 공유 비밀 키라는 설명을 접했다. 사용자 OAuth 흐름과 Engine API 통신의 인증 방식 차이를 직접 검증하지는 않았다.
- 에이전트가 제시한 `Serve` 반복문은 개념적 의사 코드다. 실제 표준 라이브러리 구현을 함께 추적한 결과로 간주하지 않는다.

## 4. 실무 역량 증거

- 사용자 독립 실행 산출물·명령·테스트 결과: 이번 세션에는 없음.
- 에이전트 수행: `rg`와 `Get-Content`로 로컬 선언·호출·구현을 확인했다. API 등록과 콜백 조회·실행 위치를 소스로 확인했으며 네트워크 요청으로 검증하지 않았다.
- 문서 산출물: 이 작업일지와 `CAREER_PLAN.md`의 날짜별 추가 관찰. 에이전트가 대화 근거를 정리한 것이며 사용자의 독립 작성·구현 증거는 아니다.
- 일반 실행의 시작·RPC 요청 처리 경로를 읽었다. 개발 모드·부하 테스트 경로, 실제 Lighthouse 연결, 운영 장애는 검증하지 않았다.

## 5. 다음에 확인할 작은 과제

아래는 제안이며 아직 수행하지 않았다.

1. 소스를 보며 `New → openEndpoints → startRPC → start → ServeHTTP`를 자기 말로 설명하기. 통과 기준: P2P 분기와 RPC 분기를 구분하고 객체 생성·처리기 등록·포트 열기·요청 처리 시점을 혼동하지 않는다.
2. `httpHandler.Store`와 `Load` 한 곳씩을 직접 찾아 연결하기. 통과 기준: 저장되는 값과 반환 타입이 `*rpcHandler`임을 설명하고, 임베디드 Handler가 실제 호출에 어떻게 연결되는지 짚는다.
3. `eth_blockNumber`의 등록과 실행 위치를 직접 찾기. 통과 기준: namespace·서비스 객체·등록된 메서드 조회·실제 호출을 근거 코드와 함께 구분한다.

## 6. 취업 관점

블록체인 백엔드의 RPC 통합, 노드 인프라의 접점·인증 설정, 클라이언트 코드 탐색과 관련된 기초다. 현재 증거는 설명을 받으며 일부 관계를 재구성하는 수준이다. 안내가 있는 코드 읽기와 흐름 문서화 과제를 시도할 근거는 있지만, 독립 업무 수행을 맡길 수 있다고 판단할 증거는 부족하다.

구현·테스트, 인증 실패 재현, 실제 노드 운영, 성능·장애 분석, 동료 협업은 이번 대화로 평가하지 않는다. 목표 직무는 확정하지 않았다.

## 7. 탐색 방식과 범위

큰 실행 구조를 따라가면서 필요한 문법과 개념을 세부 확인하는 방식이었다. `node.go`의 시작 경로에서 `rpcstack.go`의 Handler 구성·요청 분기로 들어가고, API 등록·호출 위치를 확인했다. JWT에서 웹 로그인과 OAuth로 확장한 뒤 다시 Engine API 인증으로 돌아왔다.

깊이는 객체 관계·실행 시점·인터페이스 전달·문자열 조건 해석에 집중됐다. Go 네트워크 런타임, 실제 `net/http.Server.Serve` 내부, WS 프레임 처리, JWT 암호 알고리즘까지 분석한 세션은 아니다.

## 8. 질문·협업 방식

- 11월 6~7일 기록의 이름·역할·데이터 흐름 확인에 이어, 오늘도 “이름은 http라고 지었지만 ws도 관여하는거야?”, “ServeHTTP … 이름만 같은거지?”처럼 이름과 실제 처리 대상을 대조했다. 인터페이스 경계를 확인하는 업무에 도움이 될 가능성은 있으나 실제 리뷰 성과는 미검증이다.
- “언제 실행을 했고 왜 요청으로 보내면 받게 되는거야?”라고 준비 코드와 실제 수신 사이의 연결을 요구했고, 설명 후 `Serve` 반복문과 고루틴 관계를 재진술했다. 설명을 실행 모델로 연결하려는 행동이 관찰됐다.
- API·OAuth·JWT를 같은 분류로 묶어도 되는지 질문하고, 네이버 지도 사례로 사용자 권한 위임이 필요한 상황을 구별하려 했다. 개념의 적용 범위를 사례로 확인하는 접근이다. 보안 설계 능력이나 독립 구현으로 확대하지 않는다.
- 이는 에이전트와의 질의응답 관찰이다. 질문 수로 생산성·소통 비용을 평가하지 않으며 반복 질문의 원인은 확정하지 않는다. 실제 코드 리뷰, 역할 분담, 일정 조율과 독립 전달 문서는 다음 관찰 대상이다.
