## 3. 이전 혼동과 현재 상태

- 에이전트가 처음에 USDC를 보유한 체인으로 입금 체인을 바꾸면 되는 것처럼 안내했다. 실제 연결 지갑의 USDC 목록에는 Arbitrum 계열과 HyperEVM만 있었고 Ethereum은 없었다. 공식 문서의 이메일 로그인용 Ethereum USDC 전용 입금 경로와 현재 지갑 입금 경로를 구분해 정정했다. 같은 계정에서 그 전용 경로를 사용할 수 있는지, 업비트가 해당 수신처 출금을 허용하는지는 미확인이다. “1 USDC만 내면 Hyperliquid 입금까지 완료”로 기록하지 않는다.
- Arc와 Arbitrum은 별개 네트워크다. 같은 USDC 또는 같은 주소 형식이라는 이유로 다른 체인 입금을 지원하는 것은 아니다. Ledger Ethereum 주소에 받는 것과 Hyperliquid 담보 입금도 별개라는 설명을 접했다. 실제 이동으로 검증하지 않았다.
- 업비트는 건당 정액 출금료를 네트워크 전송 비용으로 사용한다고 안내한다. 특정 건의 실제 가스비와 정확히 같거나 차액 전부가 거래소 이익이라는 증거는 없다. 지갑을 거쳐도 업비트 출금료 자체가 사라지지 않는다.
- 2배 롱의 약 49% 하락 청산은 단일 포지션·담보·유지증거금·비용 가정에 따른 예시다. 버튼 배율만으로 실제 청산가를 확정하지 않으며 Cross의 다른 잔액·포지션, 펀딩비와 마크 가격에 따라 달라질 수 있다. 실제 포지션 청산가는 확인하지 않았다.
- Hyperliquid에서 에이전트가 배율에 `1.5`를 입력했을 때 UI가 `2`를 표시했다. 저장하지 않고 기존 `20` 입력을 복원했다. 해당 UI 관측이며, 실효 배율을 소수로 맞추는 모든 방법이 금지된다는 뜻은 아니다. 포지션 규모와 담보로 실효 배율을 구분하는 설명을 접했다.
- 견적 평가액과 예상 수령액 차이는 슬리피지 그 자체가 아니다. 수수료·스프레드·체인 이동 비용 등이 섞일 수 있다. 마지막 상세 화면에 `최대 슬리피지 0%`와 변동 환율 표시가 함께 있었지만, 실제 최소 수령액·표시 규칙·실행 보장 조건은 확인하지 않았다. 무비용이나 무조건적인 체결 보장으로 해석하지 않는다.
- DEX가 항상 불리하거나 유동성 부족이 항상 원인이라는 결론은 확정하지 않았다. 소액의 고정 비용, 중개·브리지 경로와 실제 풀 유동성을 구분해야 한다는 설명을 접했다.

## 4. 실무 역량 증거

- 사용자 산출물: 스크린샷, 네트워크별 출금료 제시, 환율 계산식 제안, 2회 송금 비용 합산, 차익거래 가설 발언. 재현 가능한 코드·테스트·송금·체결 산출물은 없다.
- 에이전트 계산: 사진의 `1 TRX = 0.311815 USDC`와 09:47 KST에 조회한 Bybit 최근 체결가 `0.3175`를 비교했다. `(1 - 0.311815 / 0.3175) × 100 ≈ 1.79%` 차이다. 최근 체결가는 매도 주문의 실행 가능 매수호가·깊이를 검증한 값이 아니며 사진과 조회도 동시가 아니다.
- 입력 `24.701562 TRX`를 위 두 환율로 환산하면 약 `7.7023`, `7.8427 USDC`, 차액 약 `0.1404 USDC`다. 별도 가스비 `$0.35`가 추가 지출된다는 가정이면 총 차액 약 `$0.4904`, 총지출 대비 약 `5.99%`다. USDC≈USD 가정과 시점 차이가 있는 근사 비교이며 실제 체결 손실·실제 슬리피지 측정은 아니다.
- 사진마다 도착 체인과 예상 수령량이 바뀌었다. 서로 다른 견적을 하나의 거래로 합치지 않는다. 이 비교만으로 유동성 부족이나 각 수수료의 정확한 비중을 특정하지 못했다.
- 도움 범위: 브라우저·공식 문서 조회와 수치 계산은 에이전트가 수행했다. 사용자의 독립 시세 조회·계산·온체인 잔액 대조 결과는 아니다.
- 기록 산출물: `notes/2026-11-10-study-log.md`. 기존 일지·소스는 보존하고 오늘 기록만 작성했다. 커밋·푸시는 실행하지 않았다.

## 5. 다음에 확인할 작은 과제

모두 제안이며 아직 수행하지 않았다. 우선 자금 송금 없이 확인한다.

1. 입금 경로 하나를 끝까지 검증하기. 통과 기준: 출발처, 자산, 네트워크, 수신 계정, 최종 담보 도착처와 각 단계 비용을 구분한다. 미지원 체인을 배제하고 계정·토큰 컨트랙트·브리지 주소를 혼동하지 않는다.
2. 동일 시각 견적 비교를 직접 기록하기. 통과 기준: 같은 입력량·출발/도착 체인의 2개 견적에서 단위 환율, 별도 가스비, 최소 수령액·허용 슬리피지, 참고 시세와의 차이를 중복 없이 계산한다. 안 보이는 값은 미확인으로 남긴다.
3. AMM 가격 조정 예시를 계산하기. 통과 기준: 수수료를 우선 제외한 `x*y=k` 풀에서 소량·대량 매수의 평균 가격과 거래 후 가격을 구분하고, 비용이 있으면 모든 가격 차이가 차익거래 이익은 아닌 이유를 자기 말로 설명한다.

## 6. 취업 관점

지갑·거래소 연동 및 DeFi 백엔드의 자산/네트워크 식별, 입출금 경로 검증, 견적·수수료 명세 해석과 관련된 기초다. 화면 용어를 실제 자산 이동·비용과 대조하는 문서화 과제로 연결할 관찰은 있다.

현재는 설명을 받으며 일부 관계를 연결한 증거다. 지갑 API·RPC 연동 구현, 토큰 검증 자동화, 트랜잭션 시뮬레이션·서명·영수증 처리, 체결·브리지 장애 분석은 미확인이다. Geth·Lighthouse 구현·노드 운영 능력이나 회사에 대한 입증된 기여로 환산하지 않으며 목표 직무를 새로 확정하지 않는다.

## 7. 탐색 방식과 범위

ETH 2배 롱 사용 흐름에서 담보, 출금 네트워크, Ledger 주소, 비용, 스왑 환율, DEX 가격 형성으로 범위를 확장했다. 중심은 화면 기반 개념 정리와 경로·비용 구분이며 공식 문서와 외부 시세를 보조 근거로 사용했다.

AMM 가격 조정의 직관까지 논의했지만 실제 풀 주소·준비금·라우팅 알고리즘·수수료 코드·브리지 구현·MEV 동작은 추적하지 않았다. 컨트랙트 검증이나 온체인 실행 분석 세션은 아니다. 소액 견적 하나를 DEX 전체의 통계적 결론으로 확대하지 않는다.

## 8. 질문·협업 방식

- 11월 7일 endpoint, 11월 9일 Handler/미들웨어 기록처럼 용어와 실제 역할을 대조하는 접근이 오늘도 관찰됐다. “저걸 왜하는거야? … 업비트에서 직접 … ERC기반으로”라고 출발 조건을 다시 제시해 일반 안내가 현재 화면에 적용되는지 확인했고 설명이 정정됐다. 요구사항 전제 확인에 도움이 될 가능성은 있으나 실제 업무 효과는 미검증이다.
- “가스비는 아니고 업비트가 그냥 가져가겠다는거야?”라며 표기 비용의 수취·사용 주체를 구분하려 했다. 실제 수익 구조를 입증한 분석과는 구분한다.
- “실제 기준 환율은 어디서”, 이어 “그래서 실제 환율은 얼마고 얼마나 차이나는대?”라고 비교 방법 설명에서 수치 검증으로 돌아오도록 요청했다. 의사결정에 필요한 근거를 요구한 사례이며 계산은 에이전트가 했다.
- 차익거래로 유리한 가격이 조정된다는 가설로 개별 견적에서 가격 형성 구조로 확장했다. 검증할 가설을 제안한 관찰이지 독립 수학 설명·알고리즘 분석 증거는 아니다.
- 반복 질문에는 부정확한 네트워크 안내, 스크린샷 변경, 에이전트의 실제 시세 조회 지연도 영향을 줬을 수 있다. 이해력·생산성·소통 비용으로 단정하지 않는다. 동료와의 리뷰·역할 분담·일정 조율은 미확인이다.

- **브리지와 서명:** Circle CCTP의 USDC 소각·발행 이동과 ETH 공식 브리지의 보관·출금 구조를 혼동하지 않는다. USDC의 체인 이동과 USDC→ETH 교환도 다르다. 지갑 앱을 연결하는 것과 복구문구를 가져오는 것은 다르며, 복구문구 입력을 안내하지 않았다.
- **초기 가스비 문제:** ETH가 없는 상태의 일반 Arbitrum USDC→ETH 스왑은 승인·실행 단계에서 막힐 수 있다. Solana에서 출발해 Arbitrum ETH를 받는 견적에서는 사용자의 출발 거래 비용과 서비스 측 목적지 전송 비용을 구분해야 한다. 목적지에서 받기만 하는 데에는 수령자의 기존 ETH가 필요하지 않다. 견적 화면을 실제 교환 완료 증거로 기록하지 않는다.
- **경로 권고 정정:** 거래소 직접 출금·가스리스 스왑의 일반 지원만으로 현재 계정에 저렴하고 실행 가능한 경로라고 단정하면 안 된다. 최소금액·고정료·출발 가스·하드웨어 계정 호환·스마트 계정 요구를 확인해야 한다. 앞선 에이전트 권고는 일부 조건 확인이 부족했으며, 미검증 경로를 성공 사례로 남기지 않는다.
- **주문 상태:** Market은 현재 호가에서 체결을 시도하고 Limit은 가격 조건을 지정한다. 주문 제출과 체결은 별개다. Positions의 보유 포지션과 오른쪽 새 주문 입력값을 구분해야 한다. 주문창의 예상 청산가를 기존 포지션의 청산가로 해석하지 않는다.
- **종료와 강제청산:** Close는 포지션을 줄이거나 닫는 거래이고 취소·원상복구가 아니다. 청산은 유지증거금 부족으로 발생한다. Stop Loss는 사용자가 별도로 설정하는 종료 조건이며 청산가와 다르다. Cross의 N/A는 당시 담보·포지션 조건의 표시이지 미래의 무청산 보장이 아니다. 추가 거래 이후의 위험을 이전 포지션 크기로 설명하지 않는다.
- **수수료와 견적:** 일반 HyperCore 주문 제출·취소에는 별도 가스비가 없고 거래 수수료는 체결된 명목가치에 적용된다. 진입·종료 양쪽 수수료, 보유 중 펀딩, 입출금·브리지 비용, 스프레드·슬리피지를 구분한다. 펀딩은 납부 또는 수취할 수 있다. 견적과 참고 시장 호가의 차이를 실제 체결 슬리피지로 단정하지 않는다.
- **Arc의 개방성:** 이용·일반 노드 운영의 개방성과 합의 검증자 참여 허가는 별개다. 공식 문서에서 PoA와 Malachite 기반 BFT 합의 설명을 확인했지만 소스·현재 검증자 집합을 직접 검증하지 않았다. 창립 기관 수·과거 활성 검증자 수·성능 시험의 노드 수를 현재 운영 노드 수로 혼용하지 않는다.

### 후속 4. 실무 역량 증거와 검증 한계

- 증거: 사용자 제공 지갑·교환 견적 캡처, 에이전트가 읽은 탐색기 성공 상태와 포지션 표, 사용자 질문·해석, 공식 문서 조회 기록이다. 개인 거래금액·수량·주소·거래 해시는 이 취업용 추가 기록에 복사하지 않는다.
- 에이전트 계산 방법: 견적 환율 = 예상 수령량 / 입력량. 같은 방향의 시장 매도 호가와 비교하고 출발·도착 체인 및 별도 비용을 구별했다. 시점 차이가 있는 참고 비교이며 실제 실행 가격 검증은 아니다.
- 설명한 계산 모델: 초기 증거금 ≈ 명목가치 / 설정 배율, 거래 수수료 = 체결 명목가치 × 적용 요율, 단순 롱 손익 = 수량 × (종료가 − 진입가). 실제 청산은 이 단순 산식만으로 결정되지 않는다.
- 한계: 거래소·지갑·브리지 API 연동 코드, RPC 잔액·이벤트 대조, 체결 이력 수집, 트랜잭션 시뮬레이션, 재현 가능한 장애 보고서는 만들지 않았다. 지갑 경고의 구체 원인은 경고 상세·실행 결과 없이 단정하지 않는다.
- 산출물은 이 파일의 추가 절이다. 문서·화면 조회와 계산에 에이전트 도움이 있었으며, 이를 사용자의 독립적인 온체인 분석 실적으로 표현하지 않는다.

### 후속 5. 다음 확인 과제와 통과 기준

새 자금 이동·주문 없이 수행할 후보이며 아직 완료 처리하지 않는다.

1. **멀티체인 실행 경로 문서화:** 출발 자산·체인, 사용자 서명 대상, 승인과 자금 이동, 각 단계 가스 납부자, 목적지 네이티브 자산과 수령 주소 검증 항목을 정리한다. 통과 기준: 일반 스왑과 크로스체인 수령의 초기 가스비 차이를 자기 말로 설명하고 미확인 경로를 표시한다.
2. **읽기 전용 상태 대조:** 공개 주소 또는 테스트용 데이터로 chainId·네이티브 잔액·토큰 잔액·거래 상태를 구분하는 최소 스크립트를 작성하고 기대 결과와 실제 결과를 남긴다. 통과 기준: 같은 주소의 다른 체인 잔액을 혼동하지 않고 RPC 실패와 잔액 부족을 구별하며 비밀키를 사용하지 않는다.
3. **주문 상태 모델과 단위 테스트:** 모의 데이터로 제출/미체결/부분 체결/전량 체결/부분 종료/종료/취소 상태 및 명목가치·증거금·수수료를 모델링한다. 통과 기준: 체결분은 취소되지 않음, 종료 주문의 포지션 축소, 배율 중복 적용 방지, 주문창 예상치와 실제 포지션 값의 구분을 테스트한다. 실제 거래 API 필드·규칙과의 대조는 별도 후속 단계로 남긴다.

### 후속 6. 취업 관점

- **지갑·블록체인 백엔드:** 체인/자산 식별, 네이티브 가스와 토큰 잔액 구분, 승인·서명·입금 상태 모델링, RPC 오류 분류에 관련된다. 현재 증거는 화면 기반 전제 확인과 개념 연결이며 API 구현 실적은 없다.
- **거래소·DeFi 백엔드:** 주문·체결·포지션 생명주기, 담보 모드, 수수료·펀딩·청산 표시를 구분하는 기초다. 주문 매칭·리스크 엔진·청산 로직을 설계하거나 운영한 역량으로 확대하지 않는다.
- **문제 해결·문서화:** 일반적인 경로 권고가 실제 비용·지갑 조건에서 실패하는 지점을 찾아 질문하고 요청자·실행자·비용 납부자를 구별하는 접근이 관찰됐다. 문서·화면을 보며 지원받는 경로 분석 과제로 연결할 수 있으나 독립 장애 대응을 맡길 근거는 아직 부족하다.
- 다음 산출물은 투자 성과가 아니라 읽기 전용 조회 코드, 상태 전이 테스트, 재현 절차와 검증 결과가 적힌 기술 문서로 삼는다. Geth·Lighthouse 소스 분석·노드 운영이나 목표 직무 확정으로 합산하지 않는다.

### 후속 7. 탐색 방식과 깊이

화면의 수수료 경고에서 체인별 가스 의존성으로, 교환 견적에서 거래 실행 주체로, 주문 입력에서 체결·담보·청산 상태로 범위를 확장했다. 중심은 제품 사용 흐름의 개념 정리와 현재 화면의 전제 확인이었다. 공식 지원 문서·참고 시세를 보조 근거로 사용했다.

EVM opcode·브리지 컨트랙트·솔버 정산·합의 엔진·매칭 및 리스크 엔진의 소스와 실행 추적까지는 들어가지 않았다. 사용 화면 관찰과 내부 구현 검증을 구분한다.

### 후속 8. 질문·협업 관찰

- “ETH를 확보하는 거래에도 ETH가 필요한가”라고 해결책 자체의 선행 조건을 짚었다. 장애 대응에서 의존성을 확인하는 강점 후보이며 실제 로그·RPC로 원인을 독립 입증한 것은 아니다.
- 일반적인 거래소 출금 안내를 실제 고정 비용과 비교해 거절하고 가능한 대안의 총비용을 요구했다. 사용자 제약을 실행 가능한 조건으로 좁히는 데 도움이 된 사례다. 이를 전반적인 비용 최적화 능력으로 일반화하지 않는다.
- 실제 화면의 주문 규모·청산가를 다시 읽어 달라고 요청해 설명을 현재 상태와 대조했다. 오른쪽 새 주문 입력과 아래 활성 포지션을 분리해야 한다는 안내로 이어졌다. 상태 확인 질문을 무능력의 증거로 보거나 반복 질문 수로 생산성을 판단하지 않는다.
- 체결 이후 취소 가능 여부와 손익 확정의 관계를 자기 말로 제시했다. 용어보다 실제 효과를 확인하는 접근으로 볼 수 있으나 힌트 없는 전체 흐름 설명은 아직 확인하지 않았다.
- 에이전트의 경로 권고·단위 해석·변경된 포지션 전제를 바로잡는 과정이 포함됐다. 반복 확인에는 안내의 한계와 화면 변화도 영향을 주었으므로 사용자 성향으로만 원인을 돌리지 않는다. 실제 동료 협업·코드 리뷰·일정 조율은 별도 관찰 대상이다.

### 오늘의 범위와 실제 수행

- 설명 접함: `Server.Start()`에서 `setupLocalNode()`, `Listening`, `setupPortMapping`, discovery, `dialScheduler`가 각각 어디에 놓이는지 개괄했다. `setupLocalNode()`는 실행 중인 이 Geth 인스턴스의 P2P 신원과 로컬 주소·검색 기능을 준비하는 경로라고 설명했다.
- 설명 접함: `crypto.FromECDSAPub(&srv.PrivateKey.PublicKey)`는 서버 개인키의 공개키를 바이트로 인코딩하는 코드이며, 공개키에서 Node ID를 만들고 핸드셰이크에서 신원을 확인하는 용도라고 설명했다.
- 설명 접함: `outHandshake`는 outbound 연결에서 진행되는 핸드셰이크의 일부라고 개괄했다. 실제 메시지, 검증 조건, 호출 관계는 확인하지 않았다.
- 사용자 수행: 해당 코드 조각을 제시하고 로컬 노드, 키의 소유 주체, 핸드셰이크 개념을 질문했다. 저장소 소스는 이 대화에서 직접 열람하지 않았고, 코드를 실행하거나 수정하지 않았다. 아래 설명은 소스 대조 전이므로 설명 접함으로만 기록한다.

### 이전 혼동과 다음 확인

- “로컬”은 네트워크 상대가 같은 컴퓨터에 있다는 뜻이 아니라 현재 실행 중인 Geth 인스턴스 관점의 자기 자신이라는 설명을 접했다. 사용자가 소스에서 이를 직접 검증했는지는 미확인이다.
- `outHandshake`의 정확한 의미는 이름만으로 확정할 수 없으므로, 다음에는 정의와 호출부를 함께 확인한다.

### 실무 역량 증거와 취업 관점

실행 산출물·명령·검증 결과는 없다. 질문은 `local`이라는 관점 용어와 핸드셰이크의 실제 역할을 구별하려는 행동으로 관찰됐다. 이는 네트워크 요구사항을 정확히 이해하는 데 도움이 될 가능성이 있지만, 코드 리뷰나 독립적인 P2P 장애 분석의 증거는 아니다. 노드 인프라·클라이언트 개발의 네트워크 기초와 관련되며 실제 구현 추적은 미확인이다.

### 탐색 방식과 다음 작은 과제

이번 대화는 큰 구조에서 세부 심볼로 범위를 좁히는 개념 설명 중심이었다. 로컬 소스의 정의·호출부 확인에는 들어가지 않았다.

1. `setupLocalNode()`에서 공개키가 Node ID로 이어지는 사용 지점을 찾는다. 통과 기준: 키 입력, Node ID 생성, local node 구성의 순서를 소스 근거로 설명한다.
2. `setupConn`에서 `outHandshake`가 실제 호출되는 경로와 검증값을 확인한다. 통과 기준: outbound 연결의 호출 순서, 성공 후 단계, 실패 시 종료 동작을 짧게 정리한다.
3. `dialScheduler`가 discovery 결과를 받아 실제 다이얼을 시도하는 연결 지점을 찾는다. 통과 기준: 발견과 접속 시도가 서로 다른 구성요소임을 호출 관계로 보여준다.
