# 2026-11-20 학습 작업일지 — RPC 콜백 실행과 HTTP 응답 연결

## 1. 오늘의 범위와 실제 수행

`handleCallMsg`에서 시작해 RPC 이름으로 콜백을 조회하고, 실제 Go 메서드를 실행해 JSON-RPC 응답 객체를 만드는 흐름을 함께 살펴봤다. 구독 요청의 별도 분기와 등록·알림 활성화 시점도 설명을 접했다. 이후 `reflect.Value.Call`에서 Go 런타임 호출까지 내려갔다가 HTTP 응답 경로로 돌아왔다.

에이전트가 로컬 Geth의 `rpc/handler.go`, `rpc/service.go`, `rpc/json.go`, `rpc/http.go`, `rpc/server.go`, `rpc/subscription.go`, `internal/ethapi/api.go`, `eth/filters/api.go`를 열람했다. 로컬 Go 표준 라이브러리의 `reflect/value.go`, `runtime/stubs.go`, `runtime/asm_amd64.s` 일부도 확인했다. 사용자 직접 코드 작성·명령 실행·결과 검증은 확인하지 않았다. 노드 실행과 Geth·Lighthouse 소스 수정은 하지 않았다.

## 2. 이해 상태

아래 판단은 모두 2026-11-20 대화에 근거한다. 설명을 들으며 연결한 범위를 독립 설명이나 독립 수행으로 올리지 않는다.

## 3. 이전 혼동과 현재 상태

- RPC `method`가 반드시 같은 이름의 Go 함수라는 모델에서 출발했다. 일반 조회는 등록된 함수로 연결되지만 `eth_subscribe`는 `handleSubscribe`가 구독 종류 문자열을 읽어 별도 처리한다는 설명을 접했다. `NewHeads` 전체가 이벤트마다 재실행되는 것이 아니라 구독 설정 시 만든 고루틴이 헤더를 받아 알림을 보낸다는 정정도 설명했다. 독립 확인은 없다.
- `callback()` 조회, `(*callback).call()` 실행 준비, `reflect.Value.Call()`의 실제 함수 호출을 구분했다. 자동 호출이 아니라 `runMethod`의 명시적 `callb.call(...)` 호출로 이어진다는 코드를 함께 봤다.
- `make([]reflect.Value, 0, capacity)`의 용량을 실제 0 요소 목록으로 해석한 질문이 있었다. 길이 0에서는 요소가 없고 첫 append가 첫 요소를 넣는다는 설명을 접했다. 직접 실험하지 않았다.
- 에이전트의 “함수를 담는다”는 축약 설명으로는 타입 정보·실제 값·호출이 충분히 연결되지 않았다. 함수 값 포인터와 코드 주소를 동일시하지 않도록 보완했고, `reflect.Value`의 타입·포인터 정보와 런타임 호출 경계를 설명했다. 저수준 구현 이해가 완료되었다고 기록하지 않는다.
- HTTP와 JSON-RPC를 서로 대체되는 응답 방식으로 읽을 가능성을 질문했다. HTTP 응답 본문에 JSON-RPC 메시지가 들어간다는 설명, `ServeHTTP(w,r)`의 `w`를 `encodeMsg`가 참조한다는 설명을 접했다. 최종 사용자 발언상 이 연결은 여전히 불확실하다.

## 4. 실무 역량 증거와 도움 범위

사용자의 독립 구현·실행·검증 산출물은 이번 세션에 없다. 소스 위치 검색, 코드 발췌, 경로 연결 설명은 에이전트가 수행했다. 실제 HTTP RPC 요청·응답 캡처, 구독 알림 수신, 오류 재현은 하지 않았다. 본 일지도 에이전트가 대화를 근거로 작성한다.

핵심 소스 참조는 다음 정도로 한정한다.

- `rpc/service.go`: `serviceRegistry.callback`, `newCallback`, `(*callback).call` — 조회·등록 정보·실행 준비 구분.
- `rpc/handler.go`: `handleCall`, `runMethod`, `addSubscriptions` — 분기·실행 결과 포장·구독 보관.
- `rpc/json.go`: `jsonrpcMessage.response`, `jsonCodec.writeJSON` — 응답 객체 생성과 쓰기 구분.
- `rpc/http.go`: `ServeHTTP`, `newHTTPServerConn`, `httpWrite` — 응답 객체 `w`의 전달.
- `internal/ethapi/api.go`: `BlockChainAPI.BlockNumber` — 실제 조회 대상.

## 5. 다음에 확인할 작은 과제

아래는 제안이며 미수행 상태다. 오늘 이해가 불확실했던 HTTP 연결을 먼저 확인한다.

1. `ServeHTTP`의 `w`에서 `w.Write`까지 변수 전달을 따라 표시하기. 통과 기준: `newHTTPServerConn`의 인자, `encodeMsg`의 클로저 참조, codec의 저장 필드, `writeJSON`의 간접 호출을 구별하고 왜 원래 요청의 응답이 되는지 설명한다. 전체 네트워크 런타임 추적은 요구하지 않는다.
2. 작은 수신 객체와 메서드를 만들고 직접 호출과 reflection 호출을 비교하기. 통과 기준: `Method.Func`에 대응하는 함수 값, receiver, 인자 목록을 직접 구성·실행하고 결과 타입을 확인한다. 도움을 받으면 범위와 수행자를 남긴다.
3. RPC의 결과+error 반환 사례 하나를 소스에서 찾기. 통과 기준: 등록 허용 조건과 `errPos` 처리, `results[0].Interface()`의 역할을 도움 없이 연결한다.

## 6. 취업 관점

RPC 인터페이스와 실행 경계를 읽는 기초로, 블록체인 백엔드 통합·노드 인프라의 요청 경로 분석·클라이언트 코드 탐색에 관련된다. 설명과 소스 안내 아래 일부 관계를 재구성한 증거가 있으며, 이를 바탕으로 작은 흐름 추적 과제를 시도할 수 있다. 독립 RPC 구현·장애 분석·운영·성능 검증을 맡길 수 있는지 판단할 수행 증거는 없다. 목표 직무를 코어 클라이언트 개발로 확정하지 않는다.

## 7. 탐색 방식과 범위

RPC의 큰 실행 경로에서 출발해 map 조회, callback 구조체, 메서드 수신자, reflection 반환값을 세부 확인했다. 표준 라이브러리의 함수 정보·인자 배치와 런타임 어셈블리 호출 지점까지 일부 코드를 열람했지만, ABI·어셈블리·메모리 안전성을 독립 분석한 세션은 아니다. 마지막에는 HTTP 응답의 `ResponseWriter` 전달과 클로저 참조 연결로 돌아왔다. 중심은 코드 독해와 개념 연결이며 실행 검증은 없었다.

## 8. 질문·협업 방식

- “실제 fullargs만드는 코드 어디서봐야돼?”, “코드 집어서 설명해줘”라고 요약 설명의 근거를 실제 구현 위치로 요구했다. 11월 9일 일지의 선언·구현 위치 확인과 유사한 접근이 오늘도 관찰됐다. 추상화 경계의 가정을 확인하는 작업에 도움이 될 가능성이 있으나, 실제 버그 발견·리뷰 성과는 미검증이다.
- “그건 규칙으로 리턴을 하나만 하게끔 한거라서”라고 적용 범위를 Geth 전체에서 RPC 등록 함수로 좁혀 재구성했다. 에이전트가 결과와 error 구분을 보완했으므로 독립 설명으로 보지 않는다.
- 이해되지 않은 상태를 “아직 잘 모르겟다”라고 알리고 일지 작성으로 세션 종료를 요청했다. 설명을 들었다는 이유만으로 이해 완료를 추정하지 않을 직접 근거다. 반복 질문에는 에이전트 설명의 추상성·변수 범위 생략도 관련되어 있어, 사용자 기억·학습 속도나 소통 비용으로 원인을 단정하지 않는다.
- 이 기록은 에이전트와의 질의응답 관찰이다. 팀 코드 리뷰·역할 분담·일정 조율·문서 전달 역량의 증거로 확대하지 않는다.
