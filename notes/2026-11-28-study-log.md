# 2026-11-28 학습 작업일지 — RPC 거래 제출과 멤풀, Add의 완료 대기 범위

## 1. 오늘의 범위와 실제 수행

`SubmitTransaction`에서 `EthAPIBackend.SendTx`, `TxPool.Add`, 일반 거래를 담당하는 `LegacyPool.Add`로 이어지는 경로를 다뤘다. 에이전트가 로컬 구현과 호출부를 열람하고, 사용자는 멤풀의 역할·공유 인스턴스·인자와 반환값·비동기 처리 경계를 질문했다. 사용자 직접 소스 탐색, 코드 수정, 테스트 및 노드 실행 증거는 없다. 에이전트도 노드를 실행하거나 Geth·Lighthouse 소스를 수정하지 않았다.

## 3. 이전 혼동과 현재 상태

- 에이전트가 처음 사용한 “추가 시도”, “후속 정리”는 처리 시점과 구체적 작업을 충분히 드러내지 못했다. 사용자의 재질문 후, 일반 거래 경로에서 검증·자료구조 삽입은 호출 중 처리하고, 별도 고루틴의 분류 작업 완료를 기다릴지는 `sync`로 결정한다고 구체화했다. 사용자의 재설명이나 실행 검증은 없다.
- `sync=false`는 생략 가능한 기본 인자가 아니다. `SendTx` 호출부가 명시적으로 `false`를 전달한다. 일반 거래의 `LegacyPool.Add`는 분류 요청 후 받은 `done` 채널을 `sync=true`일 때만 기다린다. `false`여도 요청 전달 등의 대기는 있을 수 있으므로 “전혀 기다리지 않는다”는 의미는 아니다.
- 새 일반 거래는 보통 `queue`에 들어간 뒤 `promoteExecutables`에서 순서·잔액 등의 조건에 따라 `pending`으로 이동한다. 기존 pending 거래의 교체 등 다른 경로도 있어 모든 거래가 항상 같은 단계를 거친다고 일반화하지 않는다. 후속 작업에는 크기 제한 적용과 새 거래 이벤트 알림도 포함된다.
- `false` 반환 시점에 후속 작업이 이미 끝났을 수도 있고 진행 중일 수도 있다. `true`는 해당 내부 작업 완료를 기다리며, 블록 포함·EVM 실행·피어 전파 완료를 기다리는 옵션이 아니다. `pending` 승격도 실제 잔액 변경이 아니다.
- nonce 6이 대기 중일 때 nonce 5를 추가해 두 거래가 pending 후보가 되는 예시는 다른 조건을 만족한다는 가정의 설명용 사례다. 실제 실행 결과가 아니다.
- `b.eth.txPool`은 노드의 `*txpool.TxPool` 참조이며, 일반 거래 풀과 blob 거래 풀을 통합하는 관리 창구다. 노드 내 미확정 거래 관리와 확정된 체인 상태의 기준을 구분했다. blob 풀 내부 처리까지 같은 방식이라고 확인한 것은 아니다.

## 4. 실무 역량 증거와 도움 범위

사용자 증거는 위 발언에서 개념과 코드의 관계를 연결하고 불명확한 설명을 구체화해 요청한 것이다. 독립 구현·테스트·운영을 입증하는 재현 가능한 산출물은 없다.

로컬 소스 검색·열람과 설명, 본 일지 작성 및 Git 작업은 에이전트 수행이다. `rg`와 `Get-Content`로 아래 심볼을 확인했다. 명령 실행은 소스 확인을 위한 것이며 노드 동작 검증이 아니다.

- `go-ethereum/internal/ethapi/api.go`: `SubmitTransaction` 및 호출부
- `go-ethereum/eth/backend.go`: `txPool` 필드와 `txpool.New` 생성 위치
- `go-ethereum/eth/api_backend.go`: `EthAPIBackend.SendTx`
- `go-ethereum/core/txpool/txpool.go`: `TxPool`, `Add`
- `go-ethereum/core/txpool/legacypool/legacypool.go`: `Add`, `add`, `requestPromoteExecutables`, `scheduleReorgLoop`, `runReorg`
- `go-ethereum/eth/handler.go`: `txBroadcastLoop`

## 5. 다음에 확인할 작은 과제와 통과 기준

아래 과제는 제안이며 미수행이다. 기존 과제 완료 상태는 변경하지 않는다.

1. `LegacyPool.Add`의 처리 순서를 직접 표시하기. 통과 기준: 검증·보관, 분류 요청, `if sync { <-done }`을 구분하고 `false`에서도 보관 시도가 반환 전에 이루어짐을 설명한다.
2. 다음 nonce가 5이고 nonce 6이 queue에 있는 사례를 설명하기. 통과 기준: 다른 조건 충족을 가정하고 nonce 5 추가 후 queue와 pending의 변화를 설명하며, 승격과 실제 실행을 구분한다.
3. `txPool` 생성과 참조 경로를 직접 찾기. 통과 기준: `txpool.New` 결과가 `eth.txPool`에 저장되고 `b.eth`가 기존 Ethereum 인스턴스를 참조함을 소스로 보여준다.

## 6. 취업 관점

블록체인 백엔드의 RPC 접수와 온체인 완료 구분, 노드 인프라의 멤풀 상태 해석, 클라이언트 개발의 공유 객체·고루틴·완료 채널 이해와 관련된다. 코드와 운영 용어를 연결하는 기초 관찰은 있으나, 독립 경로 추적·동시성 구현·풀 상태 재현·운영 장애 분석은 미확인이다. 이번 질문만으로 맡길 수 있는 구현·운영 업무를 확정하지 않는다.

## 7. 탐색 방식과 범위

큰 흐름 파악에서 출발해 `Add` 한 줄의 타입·반환값과 완료 대기 범위를 세밀하게 확인하는 세션이었다. 에이전트는 일반 거래 경로의 스케줄러와 완료 채널까지 열람했으나, 사용자가 해당 구현을 독립 분석했다고 기록하지 않는다. 검증 알고리즘 전체, blob 풀 내부 처리, 개발 모드·부하 테스트 전용 경로 및 실제 전파·블록 생성은 분석·실행하지 않았다.

## 8. 질문·협업 방식

사용자는 “우리가 말하는 맴풀에 보관된다고하는 장소”, “내 노드에서 SSOT”라는 표현으로 익숙한 개념과 코드의 실제 관리 주체를 연결해 확인했다. 이어 “뭘 기다리지 않는다는거야”라고 물어, 추상적인 비동기 설명을 작업과 완료 시점으로 구체화하도록 요청했다. API의 완료 의미나 책임 경계를 논의할 때 도움이 될 가능성이 있다.

다만 실제 동료와의 코드 리뷰·역할 분담·일정 조율·문서 전달 성과는 관찰하지 않았다. 재질문의 원인을 사용자 능력이나 기억 문제로 단정하지 않으며, 이번에는 에이전트 설명의 모호함도 있었다. 다음 관찰 지점은 사용자가 처리 단계를 직접 정리하거나 소스의 완료 신호를 찾아 설명하는 과정이다.
