# 2026-11-25 학습 작업일지 — AccessList와 SetCode의 실행 계정 구분

## 1. 오늘의 범위와 실제 수행

11월 24일 작업일지를 읽고 다음 코드 추적 지점을 확인했다. 이후 사용자가 AccessListTx를 아직 이해하지 못했다고 밝혀, AccessList의 주소·저장 키와 접근 비용을 먼저 설명했다. SetCodeTx에서는 코드가 저장된 주소, 실행되는 계정, ERC20 approve의 호출자를 구분하는 데 집중했다.

에이전트가 로컬 `core/types/tx_access_list.go`, `core/types/tx_setcode.go`를 열람하고 EIP 및 지갑 공식 문서를 확인했다. 사용자는 호출 경로를 재작성하고 조건을 바꾸어 질문했다. 사용자 직접 구현·명령 실행·트랜잭션 생성·전송은 없었다. Geth·Lighthouse 소스 수정과 노드 실행도 없었다. 어제 제안한 DynamicFeeTx.decode → setDecoded 추적과 RPC 제출 경로 복귀는 진행하지 않았다.

| 주제 | 관찰된 사용자 발언·행동 | 판단 | 아직 확인하지 못한 부분 |

## 3. 이전 혼동과 현재 상태

- AccessList는 실행할 작업이나 접근 허가가 아니라 주소·저장 키를 미리 적는 정보라고 설명했다. 등록 비용을 먼저 내므로 항상 가스가 절감되는 것은 아니다. 접근 비용과 저장 값 변경 비용의 차이는 설명을 제공했으나 사용자 독립 계산은 없다.
- SetCode를 “B의 코드를 A의 동작 방식으로 사용한다”라고 설명한 표현이 추상적이었다. 사용자는 B가 배포자 EOA인지, B의 실행 권한을 A에게 넘기는지 반복해 확인했다. 에이전트는 B를 코드가 배포된 주소로 고정하고, B의 권한·자산을 이전하는 것이 아니라고 정정했다. 반복 질문을 사용자 능력이나 소통 비용의 증거로 해석하지 않는다.
- 사용자의 “컨트랙트 기반일 때 쓰는가”를 에이전트가 일반 컨트랙트 호출과 같은지 묻는 것으로 해석해 불필요한 구분을 추가했다. 사용자가 질문 의도를 다시 제시해, 실제 기능 실행에는 배포된 코드가 필요하다는 취지를 확인했다. 이는 설명·의도 파악의 문제도 포함한다.
- 일반 호출에서는 B가 token.approve를 호출하여 B의 allowance를 설정한다. A에 위임 설정 후 A를 호출하면 B의 바이트코드를 A의 상태에서 실행하여 A의 allowance를 설정한다는 예시를 제공했다. approve가 토큰을 즉시 이동시키는 것은 아니며, 교환 시 transferFrom을 위한 승인은 여전히 필요하다.
- SetCode가 approve와 swap을 자동으로 합치는 것은 아니다. 여러 호출을 순서대로 수행하는 지갑 코드가 필요하며, 코드 실행 권한 검사도 필요하다. 초기 의사 코드가 이를 생략했음을 명시했다.
- 마지막 정리에 대해, 트랜잭션에는 런타임 바이트코드 전체가 아니라 위임 대상 주소와 승인 정보 등이 들어가고, 설정할 EOA A의 서명이 필요하다고 설명했다. A에 위임 표시가 남으며 설정이 트랜잭션 후에도 유지됨을 설명했다. 정정 후 사용자 재설명은 아직 없다.

## 4. 실무 역량 증거와 도움 범위

사용자의 독립 구현·테스트·운영을 입증하는 재현 가능한 산출물은 없다. 호출 그림과 Solidity 형태의 코드는 설명용이며 실행 결과가 아니다. 소스 열람·웹 대조·일지 작성·Git 작업은 에이전트가 수행한다.

필요한 소스 근거:

- `go-ethereum/core/types/tx_access_list.go`: AccessTuple, AccessListTx의 필드.
- `go-ethereum/core/types/tx_setcode.go`: SetCodeTx.AuthList, SetCodeAuthorization, AddressToDelegation의 위임 표시 구성.

로컬 SetCodeTx 주석에는 temporarily라는 표현이 있으나, 오늘 설명은 지속되는 위임을 정의한 공식 EIP에 근거했다. 로컬 실행 처리 전체와 규격의 일치 여부를 검증한 것은 아니다.

참조: [EIP-2930](https://eips.ethereum.org/EIPS/eip-2930), [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702), [MetaMask 스마트 계정 설명](https://support.metamask.com/configure/accounts/what-is-a-smart-account/), [AccessList 사용 연구](https://arxiv.org/html/2312.06574v1). 사용 빈도 자료는 시점과 집계 대상이 다르며, 현재 전체 트랜잭션 대비 비율을 확정하지 않았다.

## 5. 다음에 확인할 작은 과제와 통과 기준

아래는 제안이며 미수행이다. 이전 과제도 완료 처리하지 않는다.

1. 같은 approveAndSwap 코드의 일반 호출과 위임 후 호출을 나란히 그리기. 통과 기준: 사용자가 To, 코드 원본, 실행 계정, 토큰 컨트랙트가 보는 msg.sender, allowance 소유자를 도움 없이 구분한다.
2. SetCodeTx와 AuthList를 예시로 분리하기. 통과 기준: A·B 중 누가 승인 서명해야 하는지, 바이트코드와 위임 표시의 저장 위치, 모르는 C를 임의로 변경할 수 없는 이유를 설명한다.
3. 혼동 정리 후 DynamicFeeTx.decode → UnmarshalBinary의 setDecoded까지 좁게 읽기. 통과 기준: 본문을 디코딩하는 대상과 tx.inner에 저장하는 단계를 구분한다. 이후 RPC 제출 경로로 복귀한다.

## 6. 취업 관점

호출자와 실행 계정의 구분은 지갑·블록체인 백엔드 연동, 토큰 승인 분석, 스마트 계정 기능 이해와 관련된다. 현재 증거는 조건을 바꾼 질문과 부분적 재진술이다. 안전한 지갑 코드를 구현하거나 실제 트랜잭션 추적으로 권한·자금 흐름을 검증할 수 있는지는 미확인이다.

## 7. 탐색 방식과 범위

중심은 개념 정리와 호출 경로 비교였다. AccessList·SetCode 구조체의 필드만 확인했으며, EVM 위임 실행 구현, authorization 검증의 상세 분기, ERC20·거래소 실제 구현은 추적하지 않았다. 일반 호출과 위임된 계정 호출을 설명했으며 개발 모드·부하 테스트·실행 검증은 수행하지 않았다.

## 8. 질문·협업 방식

- “B가 CA가 아니라 EOA면?”, “private인지 public인지 중요한 게 아니야?”처럼 전제를 바꿔 설명의 적용 범위를 확인했다. 11월 24일 수수료 상한의 조건을 확인한 질문과 이어지는 접근이다. 권한·예외 조건 확인에 도움이 될 가능성은 있으나 실제 업무 결과는 미확인이다.
- “B주소의 토큰 100개를 거래소 주소로 보내는 걸 허용”하는지 재진술하고, 이어 호출자를 A로 바꾼 경로를 직접 적었다. 설명을 구체적인 호출 관계로 옮기는 행동이 관찰됐다. 첫 호출 목적지는 정정이 필요했으므로 전체 경로를 독립적으로 추적했다고 보지 않는다.
- 에이전트가 질문 의도를 다르게 해석했을 때 원래 질문을 다시 제시했고, 마지막에는 “이해를 확실히 못한 것 같다”며 잠정 이해를 정리했다. 불확실한 부분을 드러내 설명을 조정하게 한 사례다. 실제 동료와의 리뷰·문서 전달·일정 조율 역량은 별도 증거가 필요하다.
