# 학습 작업일지: Geth 서비스 구성과 현재 이해 수준

- 기록일: 2026-11-06
- 범위: `eth.New`, `makeFullNode`, 서비스·API 등록, 실행 페이로드의 역할.
- 방식: 사용자 질문과 재진술, 에이전트의 설명 및 로컬 소스 확인.
- 실제 수행: 에이전트가 관련 소스를 열람했다. 이 세션에서 사용자의 코드 변경·테스트·노드 실행은 확인하지 않았다.
- 기록 원칙: 설명한 항목을 전부 습득한 지식으로 간주하지 않는다. 아래 판단은 대화에서 관찰된 범위에 한정한다.

## 여기까지는 관계를 연결한 것으로 보이는 부분

| 주제 | 관찰된 사용자 발언·행동 | 현재 판단 | 아직 확인하지 못한 부분 |
|---|---|---|---|
| 객체 생성과 서비스 등록 | `eth.New`로 만들고 `stack`에 등록하므로 Register라는 이름인지 질문했다. | 부분 이해 관찰. 생성과 등록을 연결했다. | `stack`을 P2P 서버 자체로 표현한 부분은 정정 설명을 들었다. API·프로토콜·생명주기의 차이를 독립적으로 설명하는지는 미확인. |
| 동일 객체의 참조 | 일반 Geth에서 Ethereum 인스턴스 하나를 중심으로 쓰는지 확인했다. | 부분 이해 관찰. 여러 호출 위치가 여러 인스턴스를 뜻하는 것은 아니라는 관계를 짚었다. | 포인터 전달과 객체 생성의 차이를 다른 코드에서도 구분하는지는 미확인. |
| 블록 구성 역할 | 멤풀에서 트랜잭션을 고르고 실행 페이로드를 만드는 일이 PoW 시절 miner 역할에서 남은 것인지 재진술했다. | 부분 이해 관찰. 이름의 역사와 현재 역할을 연결했다. | Engine API에서 miner까지 실제 호출 경로, 트랜잭션 선택·실행 코드는 아직 추적하지 않았다. |
| API 등록 후 요청 처리 | 지금은 stack에 넣고 나중에 사용하는 부분이 중요하겠다고 말했다. | 부분 이해 관찰. 등록과 요청 처리의 시점 차이를 짚었다. | RPC 서버가 메서드를 등록하고 요청을 분배하는 실제 구현은 아직 보지 않았다. |

위 항목은 '혼자 설명·구현할 수 있음'을 뜻하지 않는다. 독립 설명 확인 또는 독립 수행 확인으로 판정할 증거는 이번 대화에서 확보하지 않았다.

## 아직 모호하거나 설명을 접한 수준인 부분

| 항목 | 이번 대화에서 확인된 상태 | 다음에 확인할 것 |
|---|---|---|
| 실제 실행 진입점 | `miner/stress/main.go`를 일반 시작점으로 생각했다가 부하 테스트 프로그램이라는 설명을 들었다. | `cmd/geth`의 정상 호출 경로를 도움 없이 다시 찾을 수 있는가. |
| Go 리시버와 구조체 리터럴 | `s`의 의미, `[]rpc.API` 안의 두 원소와 타입 이름 생략 문법을 질문하고 설명을 들었다. | 각 변수의 타입과 참조 대상을 실제 코드에서 구분할 수 있는가. |
| backend와 APIBackend | Ethereum 변수의 역할 이름과 API용 연결 객체의 차이를 설명으로 접했다. | 함수별 반환 타입과 인자를 구분할 수 있는가. |
| 실행 페이로드 | 실행 가능한 함수 같은 것인지 질문했고 데이터 묶음이라는 설명을 들었다. | 트랜잭션 입력과 실행 결과 필드, 객체와 JSON 전달의 차이를 독립적으로 설명할 수 있는가. |
| 제네시스 초기화·피어 탐색·net RPC | 역할과 초기화 분기에 대한 설명을 접했다. | 구현과 실제 동작을 스스로 연결하는지는 아직 확인하지 않았다. |
| Engine API 요청 처리 | `catalyst.Register`의 등록 구조까지 확인했다. | forkchoiceUpdated·getPayload·newPayload의 실제 처리와 차이는 아직 미확인. |

질문과 혼동은 당시 상태의 기록이다. 설명 이후에도 계속 모른다고 단정하지 않으며, 이해가 확인되었다고 올려 적지도 않는다.

## 다시 볼 때 필요한 최소 코드 지도

경로는 `go-ethereum/` 기준이다. 전체를 숙달했다는 목록이 아니라 다음 탐색을 위한 위치다.

```text
cmd/geth/main.go: geth
  → cmd/geth/config.go: makeFullNode
      → makeConfigNode: stack과 설정 준비
      → cmd/utils/flags.go: RegisterEthService
          → eth/backend.go: New
          → tracers.APIs에 APIBackend 전달
      → eth/catalyst/api.go: Register (일반 실행 분기)
  → startNode: 구성한 노드 시작
```

변수명을 구분해야 한다. `RegisterEthService` 안의 `backend`는 `*eth.Ethereum`이다. 반환값은 `backend.APIBackend, backend`이므로 `makeFullNode`의 `backend, eth := ...`에서는 `backend`가 `*eth.EthAPIBackend`, `eth`가 `*eth.Ethereum`이다. 이름이 같다고 같은 타입인 것은 아니다.

`catalyst.Register`는 `newTestingAPI(backend)`와 `NewConsensusAPI(backend)`를 서비스로 갖는 `rpc.API` 두 항목을 등록한다. 두 번째가 인증을 요구하는 `engine` API다. 기존 Ethereum을 참조하며 새 Ethereum을 만들지 않는다. 등록 자체가 외부 합의 클라이언트 연결 완료를 뜻하지 않는다.

## 실무 능력으로 확인된 증거와 한계

오늘 관찰된 것은 설명을 바탕으로 구성 요소의 관계를 질문하고 재진술한 것이다. 독립적인 구현·테스트·운영·장애 분석을 입증하는 오늘의 산출물은 없다. 소스 조회는 에이전트가 수행했으므로 사용자의 독립 코드 탐색 증거로 계산하지 않는다. 과거 일지의 설치·실행 기록은 별도 근거이며 이번 대화만으로 수행 주체와 숙련도를 재평가하지 않았다.

현재 세션에 대한 평가는 'Geth 초기화 구조를 안내와 함께 이해하는 단계'다. 이는 사용자의 전체 개발 능력이나 지원 가능한 직급의 평가가 아니다.

## 오늘의 탐색 방식: 큰 틀을 이해하면서 의미를 구체적으로 확인

오늘은 Geth의 서비스 생성·등록과 실행·합의 계층의 경계를 이해하는 과정이 중심이었다. 질문은 객체의 정체, 참조 관계, 문법까지 구체적으로 들어갔지만 miner의 선택 알고리즘이나 RPC 디스패치 구현을 깊이 분석한 세션은 아니다. '큰 구조를 따라가며 이해에 필요한 세부를 확인한 날'로 기록한다.

| 실제 질문·행동 | 관찰과 가능한 해석 | 협업·업무에서 도움이 될 가능성 | 아직 판단할 수 없는 부분 |
|---|---|---|---|
| miner라는 이름과 현재 페이로드 생성 역할이 다르게 보인다고 질문 | 이름을 그대로 받아들이지 않고 실제 책임과 비교하는 비판적 읽기가 관찰됨 | 기존 코드의 이름과 실제 책임 사이의 오해를 줄이는 데 도움 가능 | 설계 문제나 버그를 독립적으로 발견하는 능력은 미확인 |
| 페이로드가 실행 가능한 함수 같은 것인지, 객체로 전달되는지 확인 | 추상 용어를 데이터·객체·통신 형태로 구체화하려는 접근 | API 계약과 데이터 전달 방식을 명확히 하는 데 도움 가능 | 스키마 설계·직렬화 구현 능력은 미확인 |
| Ethereum 객체가 하나인지, 리시버 s가 무엇을 담는지 질문 | 객체의 수명과 참조 대상을 명확히 하려 함 | 상태 공유나 책임 소재에 대한 대화에 도움 가능 | 포인터·공유 상태의 동작을 독립적으로 적용하는지는 미확인 |
| main·flags·stress 경로의 관계와 else 분기를 확인 | 코드 조각을 실제 실행 경로에 배치하려는 접근 | 실행 조건과 잘못된 진입점의 혼동을 줄이는 데 도움 가능 | 정상 경로를 스스로 찾는 능력은 별도 확인 필요 |
| 함수가 길다며 지금 봐야 할 부분을 질문 | 큰 구조를 파악하기 위해 탐색 범위를 조절하려는 행동 | 우선순위를 합의하며 학습·탐색할 여지가 보임 | 일정 준수와 업무 생산성은 관찰하지 않음 |
| 설명한 내용을 모두 습득한 것으로 일지에 적지 말라고 요청 | 지식 노출과 검증된 이해를 구분하는 평가 기준을 직접 제시함 | 완료 기준과 증거를 명확히 하는 대화에 도움 가능 | 실제 프로젝트의 완료 보고·리뷰 행동은 미확인 |

모호한 표현을 그냥 넘기지 않는 질문이 여러 차례 관찰됐다. 다만 질문이 자세하다는 이유로 지식이 깊다고 판단하지 않고, 기초 개념을 묻는다는 이유로 전체 개발 능력이 낮다고 판단하지 않는다. 일부 반복 질문의 원인이 기억·맥락·이전 설명 중 어디에 있는지도 확인하지 않았다.

## 협업하거나 고용할 사람이 읽을 때의 현재 요약

이 세션에서는 용어와 객체의 실제 역할을 구체적으로 물으며, 안내를 받아 시스템의 큰 구조를 구성하는 접근이 관찰됐다. 현재 근거로는 선임의 안내 아래 초기화 흐름을 읽고 불명확한 관계를 질문하는 상황을 설명할 수 있다. Geth 기능 구현·장애 대응을 독립적으로 맡길 수 있다고 판단할 증거는 부족하다.

회사 기여 측면에서는 요구사항이나 인터페이스 설명의 모호함을 발견해 확인하는 역할에 도움이 될 가능성이 있다. 실제 코드 품질 향상, 장애 감소, 일정 단축 등의 기여는 입증하지 않았다. Unity/C# 약 3년 경험은 10월 일지의 배경 기록이며, 그 분야의 성과는 별도로 확인해야 한다.

후속 대화에서 제시한 1~5점 평가는 일지 기반의 잠정 해석이며 표준화된 시험 결과가 아니다. 특히 '2/5'는 안내와 함께 이해를 연결한다는 기준의 표현으로, 전체 개발 능력의 40%나 채용 가능성을 뜻하지 않는다. 성향에는 우열 점수를 붙이지 않는다.

## 다음 확인 과제

아래는 아직 수행하지 않은 과제다. 세 개를 한 번에 할 필요는 없다.

1. 정상 Geth 실행 경로를 직접 찾아 생성·등록·시작 세 시점을 설명한다. 통과 기준: `miner/stress`와 구분하고 함수 위치를 제시한다. 힌트가 필요하면 그 범위를 기록한다.
2. `RegisterEthService`의 반환값을 따라 변수 타입을 표시한다. 통과 기준: `Ethereum`, `EthAPIBackend`, `ConsensusAPI`가 새로 만들어지는 곳과 기존 객체를 참조하는 곳을 구분한다.
3. `startNode → utils.StartNode → stack.Start`에서 API 등록 목록을 소비하는 지점을 찾는다. 통과 기준: 실제 서버 준비와 요청 처리 시점이 어디인지 코드로 설명한다. 아직 실행으로 검증한 것은 아니다.

## 취업 목표에 맞춘 기록 방식 변경

사용자는 블록체인 취업을 목표로, 자신이 모르는 것·배운 것·실제로 할 수 있는 것과 연봉 협상 근거를 객관적으로 파악하고 싶다고 밝혔다. 특히 설명한 내용을 전부 '배웠다'고 기록하면 역량이 부풀려지므로, 이해가 관찰된 부분과 미확인 부분을 나눠 달라고 요청했다.

이에 따라 [역량 기록 기준](../CAREER_PLAN.md)과 [에이전트 지침](../AGENTS.md)을 추가했다. 현재 목표 직무·기존 경력·시장 보상 자료가 없으므로 협상 가능한 연봉 금액은 미산정이다. 오늘의 대화량을 경력이나 실무 숙련도로 환산하지 않는다.

## 후반 세션: HTTP RPC 시작과 P2P의 경계

### 탐색 범위와 실제 수행

`startNode → utils.StartNode → Node.Start → openEndpoints → startRPC → httpServer.start`의 흐름을 함께 확인했다. 후반에는 서버가 실제 요청을 받는다는 의미를 이해하기 위해 TCP·UDP, 공인·사설 IP, 포트 포워딩, RLPx와 다른 블록체인의 통신 규격까지 범위를 넓혔다. 큰 구조를 이해하는 과정에서 통신 기초로 내려간 세션이다. 소켓 구현·패킷 분석·RLPx 핸드셰이크 구현을 깊게 분석한 것은 아니다.

에이전트가 로컬 코드와 공식 규격을 확인했다. 사용자 PC의 실제 공인 IP 조회, 공유기·방화벽 설정, 외부 지갑 연결, HTTP RPC 호출, 패킷 캡처는 수행하지 않았다. 대화에 등장한 IP는 설명용 예시이며 실제 사용자 IP가 아니다.

### 이해가 관찰된 부분과 아직 확인하지 않은 부분

| 주제 | 관찰된 사용자 발언·행동 | 현재 판단 | 미확인 부분 |
|---|---|---|---|
| startNode의 핵심과 보조 기능 | 지갑 이벤트 루프가 지갑 관리이며 rpcClient·ethClient가 SelfDerive에 쓰인다는 관계를 직접 설명하고, 핵심 로직은 다른 곳에 있는 것 같다고 질문 | 부분 이해 관찰. 단순 용어 확인을 넘어 코드에서 책임과 우선순위를 구분한 근거가 있음 | AccountManager 이벤트를 외부 네트워크 데이터 수신과 혼동한 표현은 정정 설명을 들음. 독립 설명은 미검증 |
| RPC 서버 준비 패턴 | HTTP·WS·Auth에서 주소·config를 설정하고 모은 서버들을 시작하는 것인지 재진술 | 부분 이해 관찰. 반복되는 설정·시작 패턴을 코드에서 추출함 | Auth는 통신 방식이 아니라 인증 엔드포인트라는 설명을 들음. 설정에 따른 공유 서버·시작 경로는 독립 추적 미확인 |
| HTTP RPC와 P2P의 분리 | 마지막에 지금 보는 httpServer.start가 P2P 시작과 별개라는 결론을 질문으로 확인 | 부분 이해 관찰. 처음 섞였던 통신 경로를 구분하는 방향으로 이동 | 같은 구분을 새로운 코드에서도 적용하는지, 두 경로를 혼자 설명하는지는 미확인 |
| 실제 HTTP 수신 | start 성공 후 주소·포트로 요청하면 응답하는지 질문 | 설명 접함. net.Listen과 Serve의 역할을 설명받음 | 직접 요청해 본 결과, 리스닝·바인딩 오류 분석 증거 없음 |
| 외부 접근 주소 | 도메인 없이 공인 IP·포트로 내 노드에 도달하는지 여러 단계로 확인 | 설명 접함. 공인·사설 IP와 포트 포워딩의 관계를 다룸 | 실제 네트워크 구성을 확인하지 않았고 CGNAT 등 조건을 사용자 환경에 적용하지 않음 |
| TCP·UDP·RLPx·eth·snap | 각 계층의 역할과 HTTP·RPC와의 관계를 반복 질문 | 설명 접함. 프로토콜 계층의 기본 구분을 배우는 중 | 독립 재설명·구현·트래픽 관찰은 미확인 |
| 다른 블록체인의 통신 | RLPx가 공통 표준인지 Fabric·비트코인과 비교 질문 | 설명 접함. 블록체인별 통신 체계가 다르다는 비교를 접함 | Fabric·비트코인 구현이나 실제 노드 간 통신은 확인하지 않음 |

앞선 다음 과제 3번은 주소·API 설정과 HTTP 수신 시작 지점까지 안내와 함께 살펴봤다. RPC 메서드 디스패치 전체의 독립 추적이나 실행 검증까지 완료한 것으로 처리하지 않는다.

### 질문 방식과 시스템 접근의 구체적 관찰

- **책임을 나누고 중요도를 고른다.** 지갑 루프를 먼저 읽은 뒤 현재 목적의 핵심이 아니라는 판단을 제시했다. 이 사례는 안내만 받은 기록과 구분해 남긴다. 업무에서 부가 기능과 조사 대상을 구분하는 데 도움이 될 가능성이 있지만, 실제 조사 효율과 성과는 미측정이다.
- **반복되는 구조를 패턴으로 묶는다.** HTTP·WS·Auth의 설정과 start 순서를 공통 흐름으로 재진술했다. 구체적인 구현을 보며 공통 구조를 추출하는 행동이 관찰됐다. 서버 운영 역량의 입증과는 구분한다.
- **추상 설명을 자신의 환경에 대입한다.** 외부 지갑, 집 PC, 유선 인터넷, 와이파이 공유기로 사례를 좁혀 물었다. 일반 설명이 실제 배치에서 무엇을 뜻하는지 확인하려는 접근이다. 네트워크를 직접 구성한 증거는 아니다.
- **기존 모델과 충돌하는 지점을 드러낸다.** 서버를 주로 HTTP·WS·API 제공으로 생각해 왔다고 밝히고 RLPx를 질문했다. 알고 있는 틀을 명시해 설명의 출발점을 조정할 수 있게 했다.
- **배운 내용을 다른 시스템으로 일반화해 확인한다.** RLPx의 설계 이유에서 Fabric·비트코인도 같은 체계인지로 질문을 넓혔다. 비교하려는 행동은 관찰되지만 각 기술의 숙련도를 뜻하지 않는다.

관찰된 범위에서는 질문을 통해 전제를 드러내고 구조를 수정하는 방식이다. 반면 오늘은 학습 범위가 네트워크 일반 개념까지 확장돼, P2P 서버의 연결·메시지 처리 구현은 아직 따라가지 않았다. 이는 세션 범위의 사실이며 산만한 성격이나 낮은 생산성으로 판정하지 않는다.

### 협업·채용 관점과 다음 확인 지점

오늘의 추가 증거는 '기존 코드에서 보조 기능과 핵심을 구분하고, 반복되는 초기화 패턴을 설명과 함께 추출할 수 있다'는 것이다. 요구사항과 시스템 경계를 확인하는 대화에 도움이 될 가능성이 있다. 실제 동료와의 리뷰·일정 조율·독립 장애 대응 능력은 여전히 미평가다.

다음에는 범위를 다시 좁혀 `p2p.Server.Start()`가 준비하는 일을 따라가거나, HTTP 이해를 확인하려면 로컬에서 RPC 요청 하나를 보내는 작은 과제를 선택한다. 두 작업 모두 아직 수행하지 않았다. 외부 공개 설정은 학습 완료 조건이 아니다.
