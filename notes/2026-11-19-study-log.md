# 2026-11-19 작업일지

## 1. 오늘의 범위와 실제 수행

11월 18일 일지를 다시 읽고, 일반 HTTP JSON-RPC 경로에서 `serveSingleRequest → codec.readBatch → readMessage → parseMessage`로 이어지는 요청 읽기·해석 구간을 살펴봤다. 사용자는 Java 디코더 취약점 기사를 `io.LimitReader`와 연결해 질문했고, 코드 탐색 중 구현 이동의 불편과 `RawMessage` 타입 선언에 대한 해석을 제시했다.

로컬 호출부·구현 및 설치된 Go 표준 라이브러리 선언의 검색·대조는 에이전트가 수행했다. 사용자가 Ctrl+F12로 구현 이동을 시도했다고 보고했지만 실제 화면과 해결 여부는 확인하지 않았다. 사용자 직접 구현·컴파일·테스트는 없었으며, Geth·Lighthouse 소스 수정이나 노드 실행은 하지 않았다.

주요 참조: `go-ethereum/rpc/http.go`의 `newHTTPServerConn`, `readAllBody`; `rpc/server.go`의 `serveSingleRequest`; `rpc/json.go`의 `jsonrpcMessage`, `readBatch`, `readMessage`, `parseMessage`, `fillMessage`. 설치된 Go의 `encoding/json/stream.go`, `v2_stream.go`, `jsontext/value.go` 타입 선언도 확인했다.

## 3. 이전 혼동과 현재 상태

- 11월 18일의 함수 준비·실행 구분에 이어, 오늘은 사용자가 `serveSingleRequest`를 실제 처리와 연결했다. 다만 전체 읽기·처리·응답 경로를 독립적으로 설명한 것은 아니다.
- `LimitReader`가 원본을 잘라 수정하는 것이 아니라 읽을 수 있는 양을 제한한다는 설명을 다시 접했다. 크기가 제한된 입력도 디코더 내부의 메모리 쓰기 오류를 유발할 수 있다는 설명 이후 사용자 재진술·검증은 없다.
- `RawMessage = Value`는 별칭이고 `Value []byte`는 새 타입 정의라는 차이를 설명했다. 타입 선언 자체가 데이터를 복사하거나 저장 공간을 생성하는 것은 아니라는 설명도 제공했다. 사용자가 이 차이를 다시 설명하거나 실행한 근거는 없다.
- 로컬 Go에는 `RawMessage []byte` 선언과 `RawMessage = jsontext.Value` 선언이 함께 있다. 실제 적용 선언은 빌드 설정에 따라 달라진다고 설명했으며, 현재 Geth 빌드에서 어느 쪽이 활성화되는지 확인하는 실행은 하지 않았다.

## 7. 탐색 방식과 범위

요청 처리의 큰 흐름을 따라가면서 입력·출력 형태와 Go 타입 의미를 세부적으로 확인하는 탐색이 중심이었다. 깊이는 HTTP 읽기 함수 연결, JSON 문법 검사, 메시지 필드 분리, `null`을 빈 메시지로 바꾸는 처리까지다. 실제 RPC 서비스 메서드 탐색·호출 및 정상 응답 쓰기 전체 경로는 추적 완료하지 않았다. 일반 HTTP 경로를 읽었으며 개발 모드·부하 테스트 경로를 실행하거나 비교하지 않았다.

보안 기사는 입력 제한과 메모리 경계의 개념 비교에 사용했다. 에이전트가 웹 검색에서 칼리프 공개 자료(https://calif.io/java4shell/)를 확인했지만 해당 원문 페이지 직접 열기는 실패했다. 취약점 구현·패치의 독립 분석이나 재현은 수행하지 않았다.

### 3. 혼동과 정정

- 에이전트가 `codec.readBatch()` 다음에 JSON 해석을 별도 단계처럼 표시했다. 사용자가 `reqs`는 이미 변환된 상태라고 지적하여, `readMessage`와 `parseMessage`가 `readBatch` 내부에서 실행된다는 도식으로 정정했다. 사용자의 시간 순서 구분을 보여 준 근거이며, 앞선 혼동에는 에이전트 도식의 영향이 있었다.
- 에이전트가 공용 handler의 응답 수신 용도와 현재 HTTP 서버 경로를 섞어 설명했다. `isResponse`는 '응답이 필요한가'가 아니라 '메시지 자체가 응답 형태인가'를 검사한다. HTTP 본문에 응답 형태 JSON이 와도 판별은 true일 수 있지만, 해당 handler의 `respWait`에 일치하는 대기 요청이 없으면 무시된다고 정정했다. 역방향 요청을 허용하지 않는 `serveSingleRequest` 경로와 공용 handler의 다른 사용 경로를 구분해 설명했으나, 사용자의 독립 경로 재설명은 미확인이다.
- `handleResponses`의 파라미터 `handleCall`은 호출자가 전달한 콜백 이름이고, `h.handleCall` 메서드와 다르다는 설명을 제공했다. 배치의 해당 콜백은 요청을 `calls`에 모으는 역할이다. 이후 실제 요청 처리는 `handleCallMsg` 등을 통해 이어진다.
- 익명 함수를 설명하려고 에이전트가 원본에 없는 `batchWork`라는 이름을 도입하자 사용자가 현재 보고 있는 `h.startCallProc(func(cp *callProc) ...)`와 연결하기 어렵다고 지적했다. 원본 코드로 돌아가 전달 함수는 `fn`, 내부 고루틴 함수는 별개라고 설명한 뒤 사용자가 파라미터 이름을 확인했다. 문법 혼동이 독립 실행으로 해소된 것은 아니다.

### 5. 다음 확인 과제와 통과 기준

1. 일반 HTTP 요청 메시지 하나를 기준으로 `readBatch` 반환부터 실제 RPC 메서드 호출까지 소스에서 잇는다. 통과 기준: 파라미터 콜백 `handleCall`과 메서드 `h.handleCall`을 구분하고, 각 단계의 입력·출력을 도움 없이 설명한다.
2. `startCallProc` 원본에서 전달 함수와 고루틴 함수를 표시하고 실행 순서를 설명한다. 통과 기준: 어느 함수가 `fn`에 들어가며 어디서 호출되는지, 배치의 요청마다 고루틴이 생기는지 정확히 구분한다.
3. `isCall`, `isResponse`, `isNotification`에 해당하는 메시지 예시를 하나씩 만든다. 통과 기준: 각 메시지의 방향·ID·결과 필드와 내부 전달 또는 응답 전송 여부를 도움 없이 설명한다.

위 과제와 앞선 과제는 완료 처리하지 않았다.

### 6. 취업 관점

함수 반환 시점과 콜백 실행 시점을 구분하고, 공용 코드에서 서버·클라이언트 역할을 나누어 읽는 능력은 Go 백엔드와 클라이언트 코드 탐색에 관련된다. 변환 완료 시점의 정정은 구체적인 관찰 근거다. 실제 비동기 코드 구현·검증, RPC 기능 추가, 장애 분석 역량으로 확대하지 않는다.

### 7. 탐색 방식과 깊이

전체 서버 구조를 잡는 질문에서 메시지 분기·채널 전달·고루틴 문법을 세부적으로 확인하는 탐색으로 이동했다. 소스 열람과 설명의 깊이는 배치 요청 분류, 응답 대기 작업으로의 채널 전달, 고루틴 준비·정리, 배치 실행 반복문과 응답 쓰기까지다. 실제 서비스 메서드 실행 내부와 실행 기반 검증은 다루지 않았다. 타임아웃·제한·추적 코드는 목적을 개괄했으며 모든 오류 경로를 분석한 것은 아니다.

### 8. 질문·협업 방식

사용자는 `reqs`가 이미 변환된 값이라는 근거로 잘못된 도식을 지적했고, 공용 handler 설명에서 외부 요청과 응답의 방향이 맞지 않는 점을 반복 확인했다. 또한 원본에 없는 변수명 도입으로 설명과 코드 위치가 어긋났음을 바로 알렸고, `fn`을 확인한 뒤에는 문법에서 실제 작업 내용으로 질문 초점을 옮겼다. 11월 18일의 준비·실행 시점 확인 및 오늘 앞선 타입·역할 확인과 유사한 행동이다.

이런 접근은 호출 관계와 설명의 일관성을 검토하는 업무에 도움이 될 가능성이 있다. 다만 반복 질문에는 에이전트의 도식·역할 구분·예시 변경도 영향을 주었으므로 이를 사용자 기억력이나 소통 비용으로 환산하지 않는다. 실제 동료 협업·일정 관리 효과는 미확인이며, 다음 관찰은 사용자의 도움 없는 경로 설명과 소스 탐색에 둔다.
