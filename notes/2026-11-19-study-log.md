# 2026-11-19 작업일지

## 1. 오늘의 범위와 실제 수행

11월 18일 일지를 다시 읽고, 일반 HTTP JSON-RPC 경로에서 `serveSingleRequest → codec.readBatch → readMessage → parseMessage`로 이어지는 요청 읽기·해석 구간을 살펴봤다. 사용자는 Java 디코더 취약점 기사를 `io.LimitReader`와 연결해 질문했고, 코드 탐색 중 구현 이동의 불편과 `RawMessage` 타입 선언에 대한 해석을 제시했다.

로컬 호출부·구현 및 설치된 Go 표준 라이브러리 선언의 검색·대조는 에이전트가 수행했다. 사용자가 Ctrl+F12로 구현 이동을 시도했다고 보고했지만 실제 화면과 해결 여부는 확인하지 않았다. 사용자 직접 구현·컴파일·테스트는 없었으며, Geth·Lighthouse 소스 수정이나 노드 실행은 하지 않았다.

주요 참조: `go-ethereum/rpc/http.go`의 `newHTTPServerConn`, `readAllBody`; `rpc/server.go`의 `serveSingleRequest`; `rpc/json.go`의 `jsonrpcMessage`, `readBatch`, `readMessage`, `parseMessage`, `fillMessage`. 설치된 Go의 `encoding/json/stream.go`, `v2_stream.go`, `jsontext/value.go` 타입 선언도 확인했다.

## 3. 이전 혼동과 현재 상태

- 11월 18일의 함수 준비·실행 구분에 이어, 오늘은 사용자가 `serveSingleRequest`를 실제 처리와 연결했다. 다만 전체 읽기·처리·응답 경로를 독립적으로 설명한 것은 아니다.
- `LimitReader`가 원본을 잘라 수정하는 것이 아니라 읽을 수 있는 양을 제한한다는 설명을 다시 접했다. 크기가 제한된 입력도 디코더 내부의 메모리 쓰기 오류를 유발할 수 있다는 설명 이후 사용자 재진술·검증은 없다.
- `RawMessage = Value`는 별칭이고 `Value []byte`는 새 타입 정의라는 차이를 설명했다. 타입 선언 자체가 데이터를 복사하거나 저장 공간을 생성하는 것은 아니라는 설명도 제공했다. 사용자가 이 차이를 다시 설명하거나 실행한 근거는 없다.
- 로컬 Go에는 `RawMessage []byte` 선언과 `RawMessage = jsontext.Value` 선언이 함께 있다. 실제 적용 선언은 빌드 설정에 따라 달라진다고 설명했으며, 현재 Geth 빌드에서 어느 쪽이 활성화되는지 확인하는 실행은 하지 않았다.

## 4. 실무 역량 증거

사용자의 재현 가능한 구현·명령 실행·테스트·운영 산출물은 이번 대화에 없다. 구현 이동 시도는 사용자 보고이며 성공 여부는 미확인이다. 에이전트는 `rg`와 소스 열람으로 호출부·구현·타입 선언을 대조하고 일지를 작성했다. 문서 작성과 이후 커밋·푸시는 에이전트의 지원 작업이며 사용자 독립 수행 증거로 인정하지 않는다. 푸시의 실제 성공 여부는 작업 완료 보고와 Git 이력으로 확인한다.

## 5. 다음에 확인할 작은 과제와 통과 기준

1. 단일 JSON 요청과 요청 두 개의 배열을 보고 `parseMessage`의 메시지 개수와 `batch` 값을 예측한다. 통과 기준: `Method`는 문자열, `Params`는 JSON 바이트로 남는다는 차이까지 도움 없이 설명한다.
2. `type A []byte`와 `type B = A`의 차이를 작은 Go 예제로 확인한다. 통과 기준: 타입 동일성과 변환 필요 여부를 먼저 예측하고 실제 컴파일 결과와 비교한다.
3. 현재 HTTP 경로의 `readBatch` 구현으로 이동한다. 통과 기준: `jsonCodec.readBatch`를 찾고 `newFuncCodec`이 반환하는 구체 타입을 근거로 해당 구현을 선택한 이유를 설명한다.

위 과제는 제안이며 실행·완료 처리하지 않았다. 전날 슬라이스 과제도 이번 대화만으로 완료 처리하지 않는다.

## 6. 취업 관점

인터페이스에서 실제 구현을 찾고 JSON 입력이 구조체로 바뀌는 경계를 읽는 일은 Go 기반 블록체인 백엔드와 클라이언트 코드 탐색에 관련된다. 오늘 관찰은 설명 지원 아래 역할과 타입의 관계를 연결한 수준이다. RPC 구현·테스트, 보안 취약점 분석·재현, txpool·EVM 처리, 노드 운영 역량은 이번 근거로 입증하지 않는다. 직무 선호도는 새로 확인하지 않았다.

## 7. 탐색 방식과 범위

요청 처리의 큰 흐름을 따라가면서 입력·출력 형태와 Go 타입 의미를 세부적으로 확인하는 탐색이 중심이었다. 깊이는 HTTP 읽기 함수 연결, JSON 문법 검사, 메시지 필드 분리, `null`을 빈 메시지로 바꾸는 처리까지다. 실제 RPC 서비스 메서드 탐색·호출 및 정상 응답 쓰기 전체 경로는 추적 완료하지 않았다. 일반 HTTP 경로를 읽었으며 개발 모드·부하 테스트 경로를 실행하거나 비교하지 않았다.

보안 기사는 입력 제한과 메모리 경계의 개념 비교에 사용했다. 에이전트가 웹 검색에서 칼리프 공개 자료(https://calif.io/java4shell/)를 확인했지만 해당 원문 페이지 직접 열기는 실패했다. 취약점 구현·패치의 독립 분석이나 재현은 수행하지 않았다.

## 8. 질문·협업 방식

사용자는 기사에서 접한 메모리 문제를 전날 읽은 `LimitReader`와 연결해 관련성을 물었고, 이어 `serveSingleRequest`의 역할, `parseMessage`의 변환 형태, 타입 선언의 연결을 차례로 좁혀 질문했다. 11월 18일의 준비·실행 구분에 이어 오늘도 이름보다 실제 역할과 데이터 형태를 확인하는 행동이 관찰됐다. 입력 처리 경계나 API 계약을 검토할 때 도움이 될 접근 후보지만 실제 업무 효과는 별도 검증이 필요하다.

“직접 찾아서 들어가는 것이 귀찮다”며 구현 이동 도구의 불편도 구체적으로 전달했다. 탐색 도구 사용법을 조정할 필요를 표현한 사례이며, 도구 문제의 원인이나 해결 결과는 미확인이다. 질문의 반복만으로 기억력·생산성·소통 비용을 추정하지 않는다. 동료와의 코드 리뷰·역할 분담·일정 조율 능력의 증거는 없으며, 다음에는 구현 탐색과 짧은 타입 예측을 사용자가 직접 수행하는 장면을 확인한다.
