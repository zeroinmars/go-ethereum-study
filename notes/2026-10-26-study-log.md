# 학습 작업일지: Node와 P2P 서버 시작 흐름

- 기록일: 2026-10-26
- 학습 범위: `p2p.Server.Start()`, NAT 포트 매핑, P2P·RPC·IPC 구분, 서비스 목록 복사와 잠금.
- 방식: 로컬 소스를 읽고 질문한 세션. 이번 세션에서 빌드·테스트·Geth 실행은 진행하지 않음.

## 오늘의 질문

`Server.Start()`는 언제 실행되는가? `setupPortMapping()`과 `Node.Start()` 안의 서비스 목록 복사는 왜 필요한가?

## 공부한 호출 흐름

```text
Geth 실행 및 설정·객체 구성
  → startNode(...)
  → utils.StartNode(...)
  → stack.Start()                    // Node.Start()
      → n.openEndpoints()
          → n.server.Start()        // p2p.Server.Start()
              → setupLocalNode()
              → setupPortMapping()
              → setupListening()    // ListenAddr 설정 시
              → setupDiscovery()
              → setupDialScheduler()
              → go srv.run()
          → n.startRPC()
      → 등록된 lifecycle.Start() 호출
```

- `Node`는 내부에 `server *p2p.Server`를 보관한다.
- `Node.Start()`와 `Server.Start()`는 이름만 같고 리시버 타입이 다른 별개의 메서드다.
- `openEndpoints()`가 실행되는 도중에 `Server.Start()`를 호출한다. 두 함수가 독립적으로 시작되는 것은 아니다.
- 일반 함수 호출은 순서대로 진행되지만, 내부에서 시작한 고루틴은 함수가 반환된 뒤에도 계속 실행될 수 있다.
- endpoint는 통신 접점이라는 뜻이다. `openEndpoints()`는 P2P와 RPC 통신 기능을 시작한다.

## NAT와 setupPortMapping

같은 내부 네트워크에서는 사설 IP로 접근할 수 있지만, 인터넷의 피어는 일반적으로 그 사설 IP에 직접 접근할 수 없다. 공유기에 외부 포트를 내부 컴퓨터의 포트로 전달하는 규칙을 만드는 것이 NAT 포트 매핑이다.

```text
외부 피어 → 공유기 공인 IP:외부 포트
                        ↓ 매핑
             내 컴퓨터 사설 IP:내부 포트 → Geth
```

- `setupPortMapping()`은 즉시 모든 매핑을 완료하는 함수가 아니라, 요청 채널과 처리 고루틴을 준비한다.
- 이후 리스닝·디스커버리 설정에서 필요한 TCP/UDP 포트 매핑 요청을 등록한다.
- `srv.NAT == nil`: 실제 매핑 없이 `consumePortMappingRequests()`로 요청만 소비한다.
- `srv.NAT`가 `nat.ExtIP`: 지정된 외부 IP를 노드 정보에 설정하고 요청만 소비한다. 이 설정 자체가 공유기 포트 포워딩을 만드는 것은 아니다.
- 그 외 NAT 구현: `portMappingLoop()`가 매핑 요청·갱신과 외부 주소 정보를 관리한다. 성공 여부는 설정과 네트워크 환경에 달려 있다.
- `loopWG.Add(1)`은 종료 시 기다릴 고루틴 하나를 등록한다. 고루틴이 끝날 때 `Done()`으로 완료를 알린다.
- `consumePortMappingRequests()`는 채널에서 요청을 꺼내고 별도 작업을 하지 않으며, `srv.quit`이 닫히면 종료한다.
- 요청을 소비하면 채널이 차서 송신자가 대기하는 상황을 방지할 수 있다. 단, 현재 구현은 버퍼 2개에 요청도 최대 2개이므로 소비자가 없다고 즉시 막히는 것은 아니다.

주소 관련해서는 `localhost`·`127.0.0.1`은 내 컴퓨터를 뜻하고, 사설 IP는 내부 네트워크에서 사용한다는 점을 구분했다. 같은 와이파이여도 서버의 바인딩 주소, 방화벽, 기기 간 통신 차단 설정에 따라 접근 가능 여부가 달라진다. IP 앞부분이 `198`이라는 정보만으로는 주소의 성격을 판단할 수 없다.

## P2P·RPC·IPC 구분

| 개념 | 의미 | Geth에서의 예 |
|---|---|---|
| P2P | 피어끼리 프로토콜 메시지를 주고받는 통신 | 실행 클라이언트끼리 블록·트랜잭션 교환 |
| RPC | 다른 프로그램이 제공하는 기능을 호출하고 결과를 받는 방식 | 지갑에서 잔액 조회, 트랜잭션 제출 |
| IPC | 같은 컴퓨터의 프로세스끼리 통신하는 방식 | 로컬 도구가 Geth에 RPC 요청 전달 |

- RPC는 웹 요청만 의미하지 않는다. Geth에서는 HTTP·WebSocket·IPC 등을 통해 RPC를 사용할 수 있다.
- RPC와 IPC는 대립하는 개념이 아니다. RPC 요청을 IPC로 전달할 수 있다.
- IPC는 Unix 계열에서 소켓 파일, Windows에서 named pipe 같은 통로를 사용할 수 있다.
- 합의 클라이언트도 Engine API라는 RPC 인터페이스를 통해 실행 클라이언트와 통신한다.
- P2P에도 요청·응답이 있지만, Geth의 JSON-RPC와는 별도의 프로토콜이다.

## 서비스 목록 복사와 잠금

```go
// n.lock을 획득한 상태
lifecycles := make([]Lifecycle, len(n.lifecycles))
copy(lifecycles, n.lifecycles)
n.lock.Unlock()

// 잠금을 해제한 뒤 복사한 목록으로 서비스를 시작
for _, lifecycle := range lifecycles {
    if err = lifecycle.Start(); err != nil {
        break
    }
    started = append(started, lifecycle)
}
```

- `make([]Lifecycle, 개수)`는 지정한 길이의 새 슬라이스를 만든다.
- `copy(목적지, 원본)`은 원본 슬라이스의 원소들을 목적지에 복사한다.
- `n.lifecycles`는 노드에 저장된 등록 서비스 목록이다. 여러 메서드에서 같은 데이터에 접근할 수 있다는 의미에서 공유된 목록이라고 설명했다.
- 잠금 안에서 읽는다는 것은 `Lock()` 이후, `Unlock()` 이전에 읽는다는 뜻이다. 같은 잠금을 사용하는 다른 고루틴은 잠금을 획득할 때까지 기다린다.
- 서비스 목록은 잠금이 걸린 동안 복사하고, 각 서비스의 `Start()`는 잠금을 해제한 뒤 호출한다.
- 잠금을 잡은 채 서비스 코드를 호출하면, 그 코드가 같은 잠금을 필요로 하는 노드 메서드를 호출할 때 서로 기다리는 교착 상태가 생길 수 있다.
- 복사되는 것은 목록의 원소다. 서비스 객체 자체를 깊게 복제하는 것은 아니다.

## 후속 학습: 고루틴과 Mutex

### 일반 함수 호출도 고루틴에서 실행된다

- Go의 `main()`은 main 고루틴에서 실행된다. 직접 `go`를 쓰지 않아도 현재 코드를 실행하는 고루틴이 있다.
- 일반 함수 호출은 현재 고루틴이 함수 안으로 들어가서 실행하고 반환하는 방식이다.
- `go 함수()`는 새 고루틴을 만들어 그 함수를 실행한다.
- 일반적인 Geth 시작 흐름에서는 main 고루틴이 `Node.Start()`와 그 안의 `Server.Start()` 호출을 담당한다. 내부의 `go srv.run()` 같은 지점부터 별도 고루틴이 실행된다.
- 리시버가 있다고 그 객체 전용 고루틴이 자동으로 생기지는 않는다.

```text
일반 호출: 같은 작업자가 main → A → Node.Start를 순서대로 수행
go 호출:   새 작업자에게 함수를 맡기고 현재 작업자는 다음 코드 진행
```

### 잠금 획득과 대기의 의미

- Mutex는 여러 고루틴이 공유 데이터를 다루는 구간을 한 번에 하나씩 실행하게 만드는 장치다.
- `Lock()`은 잠금을 선언하는 것이 아니라 획득하는 호출이다. 이미 사용 중이면 호출한 고루틴이 기다린다.
- `Lock()`에서 다음 줄로 넘어왔다면 잠금을 획득한 상태다. `Unlock()`은 잠금을 반납한다.
- 기다리는 것은 해당 고루틴이다. 프로세스 전체나 다른 고루틴의 실행까지 멈추는 것은 아니다.
- 잠금이 풀려 자신이 획득할 때까지 기다린다. 끝내 풀리지 않으면 계속 기다릴 수 있다.
- 잠금이 Node 객체 전체의 접근을 자동으로 막지는 않는다. 공유 데이터에 접근하는 코드들이 같은 잠금을 사용해야 보호된다.
- 여기서 공유 데이터는 같은 Node 인스턴스 안의 `state`, `lifecycles` 같은 필드들이다.

```text
main: n.lock 획득       → C는 n.lock에서 대기
B:    n1.lock 획득      → D는 n1.lock에서 대기
```

위 예시는 `n`과 `n1`이 서로 다른 Node를 가리킬 때다. `n1 := n`처럼 같은 Node 포인터를 복사했다면 같은 잠금을 사용한다. 기준은 변수 이름이 아니라 실제 잠금 객체다.

일반적인 Geth 실행에서는 하나의 Node 인스턴스를 중심으로 동작하지만, Node 타입이 싱글톤을 강제하는 것은 아니다.

### 왜 이미 실행 중이거나 종료된 상태에서도 Unlock을 하나

```go
n.lock.Lock()
switch n.state {
case runningState:
    n.lock.Unlock()
    return ErrNodeRunning
case closedState:
    n.lock.Unlock()
    return ErrNodeStopped
}
```

- 상태를 확인하려고 잠금을 잡았지만, 이미 시작됐거나 종료됐다면 이 호출의 작업은 끝난다.
- `return`만으로 Mutex가 자동 해제되지 않으므로 반환 전에 직접 풀어 준다.
- 잠금 해제는 다른 고루틴의 모든 작업을 허용한다는 뜻이 아니다. 다음 작업도 상태를 확인해서 가능한지 판단해야 한다.

### 같은 잠금의 실제 사용처

- `Node.Server()`: P2P 서버 포인터를 반환하는 구간.
- `Node.RegisterLifecycle()`: 노드 상태 확인과 서비스 목록 등록.
- `Node.RegisterAPIs()`, `Node.RegisterProtocols()`, `Node.RPCHandler()` 등도 사용한다.
- 예를 들어 `RegisterLifecycle()`에서 잠금을 빼면 시작 전 상태를 확인한 뒤 다른 고루틴이 노드를 시작해 버리고, 뒤늦게 서비스가 목록에 추가되는 문제가 생길 수 있다. 공유 데이터에 대한 데이터 레이스도 발생할 수 있다.

`startStopLock`과 `lock`은 같은 Mutex 타입이지만 서로 다른 객체다. `startStopLock`은 시작·종료 절차가 겹치지 않도록 보호하고, `lock`은 내부 상태와 목록 등에 접근하는 구간을 보호한다. 서비스의 `Start()`를 호출할 때 내부 `lock`은 풀지만 시작 절차의 `startStopLock`은 유지한다.

## 후속 학습: 상태 상수와 반복문 문법

```go
const (
    initializingState = iota // 0
    runningState             // 1
    closedState              // 2
)
```

- enum처럼 상태에 이름을 붙인 정수 상수다. 여기서는 별도 enum 타입을 선언한 것이 아니다.
- 타입을 명시하지 않은 정수 상수이므로 `int`인 `n.state`에 대입하거나 비교할 수 있다.

```go
var started []Lifecycle
for _, lifecycle := range lifecycles {
    if err = lifecycle.Start(); err != nil {
        break
    }
    started = append(started, lifecycle)
}
```

- 슬라이스의 `range`는 인덱스와 원소값을 제공한다. `_`는 사용하지 않는 인덱스를 버리고, `lifecycle`은 현재 원소값을 받는다.
- `if 실행문; 조건식 { 본문 }`은 실행문을 먼저 수행한 뒤 조건을 검사한다.
- 앞부분은 간단한 문장 하나이며, `{}`로 여러 문장을 묶을 수 없다. 여러 작업은 if 앞에 따로 작성한다.
- `if err := ...`는 if 범위에 새 변수를 선언하지만, 현재 코드의 `err = ...`는 기존 변수에 대입한다.
- 서비스 시작이 성공한 경우에만 `started`에 추가하고, 실패하면 반복문을 중단한다.

## 후속 학습: 배열·슬라이스와 메모리 공유

- `[3]int`는 길이 3의 배열, `[]int`는 슬라이스다. 배열은 길이도 타입에 포함되므로 `[3]int`와 `[5]int`도 다른 타입이다.
- `var started []Lifecycle`은 초기 길이 0의 nil 슬라이스 선언이다.
- `append`는 import 없이 사용하는 Go 내장 함수이며, 첫 번째 인자는 슬라이스여야 한다. 배열을 직접 전달할 수 없다.
- `started = append(started, lifecycle)`은 반환된 슬라이스를 다시 저장한다. 용량이 부족하면 내부 배열이 새로 만들어질 수 있다.
- 배열을 대입하면 원소들이 복사된다. 슬라이스를 대입하면 슬라이스 정보가 복사되며 내부 배열은 공유한다.
- 슬라이스도 값으로 전달되므로 단순히 참조 타입이라고만 외우기보다는, 내부 배열의 참조·길이·용량을 가진 값이라고 이해한다.

```go
a := [3]int{10, 20, 30}
s := a[1:3] // 원소 복사가 아니라 기존 배열의 일부 참조
s[0] = 99   // a[1]도 99로 바뀜
```

기존 원소에 대입하는 것과 `append`로 원소를 추가하는 것은 다르다. `append`가 새 배열을 만들면 반환된 슬라이스는 원래 배열과 더 이상 공유하지 않는다. 독립된 원소 저장 공간이 필요하면 별도 슬라이스를 만들고 `copy`한다. 인터페이스나 포인터 원소의 복사는 그 안의 객체를 깊게 복제하지 않는다.

## 후속 학습: Lifecycle은 객체 이름이 아니라 공통 역할

```go
type Lifecycle interface {
    Start() error
    Stop() error
}
```

- Lifecycle은 생명주기라는 뜻으로, Node가 시작·종료를 관리할 대상의 공통 인터페이스다.
- `lifecycles`는 Node 자체의 생명주기를 관리하는 객체가 아니라, Node가 관리할 객체들의 슬라이스다.
- Node는 상속 관계의 부모라기보다는 등록된 객체들을 관리하는 컨테이너다.
- 등록 예시로 `eth`, 설정에 따른 `eth.localTxTracker`, `ethstats`, `*Syncer`를 확인했다. 실제 등록 목록은 설정과 실행 경로에 따라 달라진다.
- 이 문맥에서 서비스는 기능을 담당하는 객체라는 표현이며, 별도 프로세스나 서버를 뜻하지 않는다.
- `services.eth.lifecycle`처럼 별도 생명주기 객체를 두는 구조가 아니다. `eth` 자체가 `Start()`와 `Stop()`을 제공한다.
- `lifecycles`라는 이름은 구체적인 객체 타입보다 시작·종료 가능한 공통 역할을 강조한다.

```go
// eth의 실제 타입은 *Ethereum
stack.RegisterLifecycle(eth)

// 등록 함수는 Lifecycle 인터페이스 타입으로 받음
func (n *Node) RegisterLifecycle(lifecycle Lifecycle) {
    // 잠금과 상태·중복 검사 생략
    n.lifecycles = append(n.lifecycles, lifecycle)
}
```

목록 원소의 정적 타입은 `Lifecycle`이지만, 인터페이스 값에는 실제 타입과 값이 담긴다. 실제 타입이 `*Ethereum`이면 `lifecycle.Start()`는 `(*Ethereum).Start()`를 실행한다. 객체가 새로운 Lifecycle 객체로 변하는 것은 아니다.
