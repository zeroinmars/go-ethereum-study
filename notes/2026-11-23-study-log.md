# 2026-11-23 학습 작업일지 — 트랜잭션 표현과 RLP 디코딩 입구

## 1. 오늘의 범위와 실제 수행

11월 22일 일지를 확인하고 SubmitTransaction에서 txpool 제출까지 이어 읽는 계획을 제안했으나, 실제 대화는 size 캐시의 용도, 지갑의 트랜잭션 표현·서명·전송 형식, RLP 디코딩 입구의 Go 문법을 확인하는 방향으로 진행했다. SubmitTransaction → SendTx 경로를 읽었다거나 txpool 제출 과제를 완료했다고 보지 않는다.

에이전트가 로컬 소스에서 Transaction.UnmarshalBinary·setDecoded·Size, txpool의 크기 검사·슬롯 계산, SignTx·DynamicFeeTx, rlp.DecodeBytes·streamPool을 검색·열람했다. 사용자는 코드 표현을 제시하고 의미를 질문하거나 설명을 자기 말로 연결했다. 사용자의 직접 코드 작성·명령 실행·트랜잭션 서명·RPC 전송 결과는 없다. Geth·Lighthouse 소스 수정이나 노드 실행은 하지 않았다.

## 3. 이전 혼동과 현재 상태

- 어제의 raw transaction·size 질문에서 이어, 오늘은 필드별 내부 표현, 전송용 바이트, JSON-RPC의 16진수 문자열을 구분했다. 사용자가 서명·전송 순서를 자기 말로 연결했으므로 이 연결은 부분 이해 관찰로 보완한다. 바이트 변환 실행으로 확인한 것은 아니다.
- 처음 질문에서 z와 yParity를 함께 언급했다. z는 서명 대상 해시를 정수로 해석한 입력이며 yParity와 다르다는 설명을 접했다. 정정 후 두 값을 독립적으로 구분한 재설명은 없다.
- 에이전트의 “원본 트랜잭션” 표현이 인코딩 전 필드와 raw 바이트를 오가며 모호했다. 사용자가 인코딩 전 모습이 무엇인지 반복 확인했고, 필드를 보관한 구조체·객체와 직렬화 결과로 구분해 설명을 수정했다. 반복 질문을 사용자 이해 부족으로만 해석하지 않는다.
- Stream이 미리 저장돼 있어야 Get할 수 있지 않느냐는 질문에, 풀 선언은 New 함수를 설정하며 객체가 없으면 Get이 이를 호출하고 사용 후 Put한다는 설명을 제공했다. sync.Pool의 객체 재사용은 보장되지 않는다는 설명도 접했다. 사용자 직접 실행·재설명은 없다.
- “런타임에 확인”은 타입 자체가 바뀐다는 뜻이 아니라 전달된 실제 타입을 함수 실행 중 조사한다는 뜻으로 정리했다. 현재 &data 호출에서는 포인터 여부 검사 조건이 false라는 사용자 지적을 인정하고, 다른 호출도 받는 공용 함수의 입력 검사임을 설명했다.

## 4. 실무 역량 증거와 도움 범위

사용자의 독립 구현·테스트·RPC 실행을 보여 주는 재현 가능한 산출물은 없다. 코드 검색·열람, 명세 대조, 설명용 Go·TypeScript·RLP 예시 제시, 일지 작성과 Git 작업은 에이전트가 수행한다. 대화의 예시 코드는 실제 실행 결과가 아니다.

- 소스 근거: core/types/transaction.go의 UnmarshalBinary·setDecoded·Size, core/types/transaction_signing.go의 SignTx, core/types/tx_dynamic_fee.go의 DynamicFeeTx.
- size 사용 근거: core/txpool/validation.go의 ValidateTransaction 크기 검사와 core/txpool/legacypool/legacypool.go의 numSlots. 사용자가 txpool 검증 전체를 추적한 증거로 보지 않는다.
- 디코딩 입구: core/types/transaction.go의 LegacyTx 디코딩 호출, rlp/decode.go의 DecodeBytes·streamPool과 Stream.Decode의 reflection 검사에 관한 질의응답. RLP 필드별 디코더 전체 분석은 하지 않았다.
- 공식 대조 자료: [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)의 서명 대상과 서명 포함 트랜잭션 형식. 암호학 계산을 구현·검증한 것은 아니다.

## 5. 다음에 확인할 작은 과제와 통과 기준

아래는 제안이며 미수행이다. 이전 일지의 과제도 완료 처리하지 않는다.

1. 현재 멈춘 Stream.Decode에서 포인터 검사 이후 실제 디코더 선택 지점까지만 이어 읽기. 통과 기준: val의 실제 타입, Elem의 대상, 선택된 디코더가 결과를 쓸 대상을 구분한다. 모든 reflection·RLP 내부를 한 번에 읽지는 않는다.
2. 작은 Go 예제에서 any에 포인터를 담고 타입 단언·Kind를 확인하기. 통과 기준: 포인터와 값 전달 시 결과 차이를 먼저 예측한 뒤 사용자가 직접 실행하고 출력·명령을 남긴다. 에이전트 도움 범위를 기록한다.
3. 이후 SubmitTransaction → SendTx의 입구로 복귀하기. 통과 기준: RPC 정책 검사와 풀 제출을 구분하고, 제출과 블록 포함·EVM 실행을 같은 완료로 설명하지 않는다. 처음에는 blob 분기를 제외한다.

## 6. 취업 관점

지갑과 노드 사이 데이터 표현을 구분하는 작업은 블록체인 백엔드 연동과 관련되고, interface·포인터·reflection·객체 풀을 읽는 작업은 Go 코드 탐색의 기반과 관련된다. 내부 표현에서 서명·전송 단계로 이어지는 사용자 재진술과 특정 호출의 검사 결과를 짚은 질문이 관찰 근거다. 실제 지갑 연동 개발, 서명 구현, 디코더 수정·테스트, 성능 개선이나 운영 수행을 입증하지 않는다.

## 7. 탐색 방식과 범위

오늘은 트랜잭션 제출의 큰 흐름을 더 진행하기보다 데이터 표현의 경계와 디코딩 입구의 문법·타입 의미를 확인하는 개념 정리가 중심이었다. 서명 전 데이터에서 JSON-RPC 전송까지의 표현을 연결한 뒤, LegacyTx를 출력 대상으로 전달하는 경로와 Stream 풀·reflection의 포인터 검사까지 살펴봤다. ECDSA 계산, 필드별 RLP 디코더 알고리즘, txpool 전체 검증·EVM 실행은 분석하지 않았다. 일반 RPC 경로의 소스 독해이며 개발 모드·부하 테스트·실제 노드 실행은 없다.

## 8. 질문·협업 방식

- “인코딩되기 전 원본 트랜잭션은 어떻게 생긴 건지”를 명시해 에이전트 설명의 추상화 수준을 조정했다. 11월 22일의 실행·응답 경계 질문에 이어, 이번에는 구조체·바이트·문자열 사이 표현 경계를 확인했다. 데이터 계약을 명확히 하는 업무에 도움이 될 접근 후보이나 실제 업무 효과는 미확인이다.
- “문법적인 거 물어본 거야”라고 질문 목적을 바로잡아, Decode의 용도보다 interface{} 자체의 의미에 초점을 맞추도록 요청했다. 원하는 설명 범위를 구체적으로 전달한 사례이며 동료 협업 전반의 증거로 확대하지 않는다.
- “이미 &data를 전달했으니 조건문은 항상 false 아닌가”라고 현재 호출부를 근거로 일반적인 런타임 설명의 적용 범위를 확인했다. 호출별 조건과 공용 함수의 계약을 구분하는 검토에 도움이 될 가능성이 있다. 독립 코드 리뷰나 오류 발견 성과는 확인하지 않았다.
- 질문 수나 반복만으로 생산성·학습 속도·고정 성향을 평가하지 않는다. 이번 대화에는 에이전트의 모호한 표현이 정정된 사례도 있다. 동료와의 역할 분담·일정 조율·문서 전달에 관한 새 증거는 없다.
