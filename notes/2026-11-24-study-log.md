# 2026-11-24 학습 작업일지 — 포인터·타입 정보와 트랜잭션 수수료

## 1. 오늘의 범위와 실제 수행

11월 23일 일지를 확인하고 `Stream.Decode`의 `cachedDecoder(rtyp.Elem())`부터 이어서 질문했다. 포인터의 주소 값과 포인터 타입 정보, 타입별 디코더의 선택과 실제 실행을 구분하는 설명을 접했다. 이후 `UnmarshalBinary`의 Legacy/typed 분기에서 EIP-2718, DynamicFeeTx의 수수료 설정, AccessList의 목적까지 개념을 정리했다.

에이전트가 로컬 `rlp/decode.go`, `rlp/typecache.go`, `core/types/transaction.go`의 구현·호출부를 검색·열람하고 공식 EIP와 ethereum.org 설명을 대조했다. 사용자는 코드 표현을 제시하고 개념을 재진술하거나 설명의 모호함을 지적했다. 사용자의 직접 구현·명령 실행·트랜잭션 생성 및 전송은 없었다. Geth·Lighthouse 소스 수정과 노드 실행도 없었다.

## 3. 이전 혼동과 현재 상태

- 어제의 reflection 검사에서 이어, 오늘은 `rtyp`이 주소 자체가 아닌 `*LegacyTx` 타입 정보라는 설명을 제공했다. 사용자가 타입과 실제 값의 층을 구분해 질문했으므로 부분 이해 관찰을 추가한다. `rval.Elem()`의 실제 대상 수정까지 독립적으로 설명한 것은 아니다.
- 에이전트가 GasFeeCap을 “전체 가격 한도”라고 불러 총수수료로 들리게 했다. 사용자가 “가스당 최대한도 가격인데 … 가스사용을 곱한 것처럼”이라고 지적하여 “기본 단가와 팁을 합친 가스당 가격 상한”으로 정정했다. 이 혼동을 사용자 지식 부족만으로 기록하지 않는다.
- 지갑 화면의 gas price 20을 GasFeeCap 20인 예시로 연결한 것은 실제 필드 매핑을 확인한 결과가 아니었다. 화면의 추천값·상한·실제 단가가 다를 수 있음을 정정했다. 특정 지갑의 직렬화 결과는 확인하지 않았다.
- Legacy도 EIP-1559 이후에는 기본 수수료 소각과 나머지 팁의 규칙이 적용된다고 설명했다. Legacy를 PoW 전용으로 보지 않으며, EIP-1559 도입과 머지는 별개라고 정리했다. 사용자의 정정 후 독립 재설명은 없다.
- AccessList는 접근 허가 목록이 아니며, 저장 공간의 최초 접근 비용과 잔액 0→양수 변경 비용은 별개라고 설명했다. 이 구분의 사용자 이해는 아직 확인하지 않았다.

## 4. 실무 역량 증거와 도움 범위

사용자의 독립 구현·테스트·운영·전송을 입증하는 재현 가능한 산출물은 없다. 설명용 포인터 코드와 수수료 숫자 예시는 실행 결과가 아니다. 소스 검색, 공식 문서 대조, 일지 작성 및 Git 작업은 에이전트가 수행한다.

필요한 소스 근거:

- `rlp/decode.go`: DecodeBytes → Stream.Decode → decoder 실행. `val`로 받은 `&data`에 결과를 기록하는 경로.
- `rlp/typecache.go`: cachedDecoder, typeCache.info, decoder 함수 타입. 타입별 캐시 조회와 없을 때 생성하는 경로.
- `core/types/transaction.go`: UnmarshalBinary, decodeTyped. LegacyTx 분기와 타입 번호에 따른 구조체 생성, `inner.decode(b[1:])` 호출까지 확인.

규격 대조: [EIP-2718](https://eips.ethereum.org/EIPS/eip-2718), [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559), [EIP-2930](https://eips.ethereum.org/EIPS/eip-2930), [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844), [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702), [가스 공식 설명](https://ethereum.org/developers/docs/gas/). 수수료 규칙 설명을 위한 참조이며 현재 네트워크 관측값을 측정한 것은 아니다.

## 5. 다음에 확인할 작은 과제와 통과 기준

아래는 제안이며 미수행이다. 이전 일지의 과제도 완료 처리하지 않는다.

1. 작은 Go 예제에서 구조체 값 전달과 포인터 전달을 비교하기. 통과 기준: 사용자가 원본 변경 여부를 먼저 예상하고 직접 실행하며, `Type.Elem()`과 `Value.Elem()`의 차이도 결과에 연결한다. 도움받은 범위를 기록한다.
2. BaseFee 10·18·21, GasFeeCap 20, GasTipCap 3인 경우를 계산하기. 통과 기준: 포함 가능 여부, 실제 팁, 실제 단가를 구분하고 gasUsed를 곱해야 총수수료가 됨을 설명한다.
3. decodeTyped에서 DynamicFeeTx.decode와 UnmarshalBinary의 setDecoded까지 좁게 이어 읽기. 통과 기준: 타입 번호를 제외한 본문, 필드를 채우는 대상, tx.inner에 저장하는 단계를 구분한다. 이후 RPC 제출 경로로 돌아간다.

## 6. 취업 관점

포인터·reflection·함수 값의 구분은 Go 클라이언트 코드 탐색에, 수수료 필드와 타입 구분은 지갑·블록체인 백엔드 연동에 관련된다. 현재 증거는 질문과 부분적인 재진술이며, 혼자 구현하거나 트랜잭션 오류를 재현·분석할 수 있는지는 미확인이다. 특정 직무 적합성이나 전체 개발 수준으로 확대하지 않는다.

## 7. 탐색 방식과 범위

오늘은 디코딩 입구의 문법과 타입·값 구분을 세밀하게 확인한 뒤 트랜잭션 형식과 수수료 개념으로 범위를 넓혔다. 중심은 개념 정리와 제한된 소스 추적이었다. RLP 필드별 디코딩 알고리즘, 실제 수수료 계산 구현, AccessList 가스 측정, Blob·SetCode 실행 경로는 분석하지 않았다. 일반 트랜잭션 디코딩 경로를 읽었으며 개발 모드·부하 테스트·노드 운영은 수행하지 않았다.

## 8. 질문·협업 방식

- “2000이라는 값이 어디를 가리킨다고 표현해도 되는가”, “타입적인 측면 … 실제 선언된 값 이야기는 아닌가”라는 질문으로 주소 값·타입 정보·실제 대상의 설명 층을 분리하려 했다. 11월 23일의 입력 포인터 검사 질문에 이어, 용어가 적용되는 대상을 확인하는 행동이 관찰됐다. 코드 리뷰에서 의미를 명확히 하는 데 도움이 될 가능성은 있으나 실제 동료 리뷰 성과는 미확인이다.
- “전체 가격 한도”가 총수수료처럼 들린다고 구체적으로 지적했다. 11월 23일의 “원본 트랜잭션” 표현 확인과 마찬가지로 에이전트 설명의 모호함을 드러내고 정정하게 한 사례다. 단위·필드 의미를 확인하는 업무와 관련될 수 있으나 생산성이나 시간 관리 효과는 관찰하지 않았다.
- min 수식에서 상한을 작게 설정한 경우를 따지고 Legacy와 차이를 질문했다. 설명을 조건과 사례로 비교하는 접근이 관찰됐지만, 이후 스스로 다른 수치를 계산하거나 구현한 증거는 없다.
- 에이전트와의 질의응답만 관찰했으므로 역할 분담·일정 조율·피드백 수용 등 실제 팀 협업 역량은 평가하지 않는다. 질문 수나 반복을 능력·성실성·소통 비용의 점수로 환산하지 않는다.
