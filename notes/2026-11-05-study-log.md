## 학습 방향

단순히 노드가 돌아가는 것을 확인하는 것보다, 업무에서 설정과 동작을 설명하고 문제 지점을 찾을 수 있는 수준을 목표로 한다. 필요한 코드를 읽고 확인할 동작이 생기면 실행한다. 전체 동기화를 먼저 끝내야 코드 공부를 할 수 있는 것은 아니다.

언어 자체를 배우는 것보다 업계에서 필요한 구현과 구조를 이해하는 데 우선순위를 둔다. 합의 클라이언트는 Lighthouse로 선택했으며, 내부 코드를 읽을 때 Rust도 익히기로 했다.

## CLI 옵션에서 세폴리아 설정으로

세폴리아 실행 옵션은 소문자 `--sepolia`다. 아래는 학습용 명령이며 오늘 동기화를 시작한 기록은 아니다.

```powershell
# go-ethereum 폴더에서 실행
go run ./cmd/geth --sepolia --datadir .\node-data-sepolia --verbosity 3 console
```

기존 데이터와 섞이지 않도록 별도 데이터 디렉터리를 사용한다. 네트워크 ID만 바꾸는 것은 세폴리아 설정 전체를 적용하는 것과 다르다.

```text
SepoliaFlag: 옵션 이름과 타입 정의
  → CLI 라이브러리가 입력을 해석
  → ctx.Bool("sepolia")로 옵션 값 조회
  → SetEthConfig(ctx, stack, &cfg.Eth)
  → cfg.Eth에 세폴리아 네트워크 설정 반영
```

`cli.Context`에 세폴리아의 전체 체인 설정이 들어 있는 것은 아니다. 실행 옵션을 조회하고, 그 값에 따라 실제 설정 객체를 수정한다. `&cfg.Eth`는 원본 설정의 주소를 전달하므로 함수 안의 변경이 원본에 반영된다.

`cmd/utils/flags.go`의 세폴리아 분기:

```go
case ctx.Bool(SepoliaFlag.Name):
    cfg.NetworkId = 11155111
    cfg.Genesis = core.DefaultSepoliaGenesisBlock()
    SetDNSDiscoveryDefaults(cfg, params.SepoliaGenesisHash)
```

- NetworkId: 피어와 통신할 네트워크를 구분하는 값.
- Genesis: 체인의 최초 블록 명세와 체인 규칙을 담은 설정. 단순히 중요하지 않은 첫 블록 한 개가 아니다.
- DNS discovery: 해당 체인의 피어 후보를 찾을 DNS 탐색 기본값. 이 설정 함수가 직접 접속하는 것은 아니다.

DNS는 이름으로 네트워크 정보를 조회하는 시스템이다. 일반적인 도메인→IP 조회 외에, Geth에서는 노드 접속 정보를 찾는 데도 사용한다. 피어 탐색에는 부트노드 등 다른 경로도 있다.

## eth.New: 설정을 실제 구성요소에 연결

주요 코드 위치:

| 위치 | 역할 |
|---|---|
| `cmd/geth/config.go`: `makeConfigNode` | 기본 설정을 읽고 노드를 만들며 SetEthConfig 호출 |
| `cmd/geth/config.go`: `makeFullNode` | RegisterEthService에 &cfg.Eth 전달 |
| `cmd/utils/flags.go`: `RegisterEthService` | eth.New(stack, cfg) 호출 |
| `eth/backend.go`: `New` | DB, 블록체인, 트랜잭션 풀, 통신 담당 구성요소 초기화 |

`eth.New`에는 세폴리아 전용 실행 분기가 따로 있는 것이 아니라, 전달받은 설정을 사용하는 공통 로직이 있다. 세폴리아 설정을 전달하면 그 설정에 맞는 서비스를 만든다. 생성·준비와 실제 서비스 시작은 구분한다.

함수 앞부분은 설정 검사와 보정이다.

- SyncMode와 HistoryMode가 유효하지 않으면 오류로 중단한다.
- Miner.GasPrice가 nil 또는 0 이하이면 기본값으로 보정한다.
- NoPruning + hash 저장 방식이면 Dirty 캐시 예산을 재배분한다.

## chainDb와 chaindata, StateDB

```go
chainDb, err := stack.OpenDatabaseWithOptions("chaindata", dbOptions)
```

- `chaindata`: 열 저장소의 이름.
- `chainDb`: 그 저장소에 접근하는 객체를 담은 변수.
- `dbOptions`: DB 캐시, 파일 핸들 수, ancient/era 저장 위치 등 DB를 여는 옵션. 세폴리아 설정은 아니다.
- `MetricsNamespace: "eth/db/chaindata/"`: 성능 통계 이름의 접두사이며 저장 경로가 아니다. 실제 위치는 datadir 등으로 결정된다.
- 이 호출 자체가 블록 다운로드나 저장을 시작하는 것은 아니다.

체인 저장소에는 블록 헤더·본문, 영수증, 상태 관련 데이터 등이 저장된다. 오래된 기록 일부는 ancient/freezer 영역에 보관될 수 있다. 블록이 디스크에 물리적으로 사슬처럼 배열되는 것이 아니라, 헤더의 부모 해시로 논리적으로 연결된다.

`state.StateDB`는 별도 DB 파일 이름이 아니다. 특정 상태를 기준으로 계좌 잔액, 논스, 계약 코드와 저장값을 읽고 수정하는 작업 객체다. StateDB에서 변경하는 것과 최종 디스크 저장은 별도 단계다.

## chainConfig, genesisHash, engine

```go
chainConfig, genesisHash, err := core.LoadChainConfig(chainDb, config.Genesis)
engine, err := ethconfig.CreateConsensusEngine(chainConfig, chainDb)
```

- `chainConfig`: 체인 ID, 하드포크 적용 블록·시간, PoS 전환 조건 등 체인의 규칙표.
- `genesisHash`: 제네시스 블록을 식별하는 32바이트 해시.
- LoadChainConfig는 DB에 저장된 체인 설정을 먼저 읽는다. 없으면 제공한 Genesis에서 가져온다. 이 함수만으로 기존 DB와 새 설정의 모든 호환성 검사가 끝난다고 해석하지 않는다.
- 빈 DB에 세폴리아 Genesis를 전달한 경우 세폴리아 규칙과 제네시스 해시가 나온다.

CreateConsensusEngine의 세폴리아 경로는 다음 객체를 만든다. 이 분기에서는 인자로 받은 DB를 직접 사용하지 않는다.

```go
return beacon.New(ethash.NewFaker()), nil
```

`engine`의 실제 객체는 `*beacon.Beacon`이고 `consensus.Engine` 인터페이스로 사용한다. 체인 DB나 규칙표 전체가 engine에 담기는 것은 아니다.

| 구분 | 역할 |
|---|---|
| consensus.Engine | Geth 내부의 합의 관련 블록 규칙 검사 객체 |
| Engine API | Lighthouse와 Geth가 실행 payload와 체인 선택 정보 등을 주고받는 통신 인터페이스 |
| BlockChain | 저장소를 사용해 블록체인을 관리하는 객체 |

engine은 부모 관계, 블록 번호·시간, PoS 헤더의 난이도, 가스 관련 규칙 등을 검사한다. 트랜잭션 실행 및 상태 루트 검증까지 전부 이 객체 혼자 처리하는 것은 아니다.

## PoW, PoS, 비콘체인과 더 머지

Difficulty 필드는 PoW 블록 헤더부터 있던 필드다. PoS에서는 해시 퍼즐 난이도로 사용하지 않고 반드시 0이어야 한다. 과거 PoW 블록에는 당시 난이도가 남아 있다.

- 비콘체인은 처음부터 PoS 합의를 위해 시작한 체인이다.
- 더 머지(The Merge)는 체인 이름이 아니라, 기존 이더리움 실행을 비콘체인의 PoS 합의와 연결한 업그레이드다.
- 기존 계좌·거래 기록은 이어지며, 새 블록을 결정하는 합의 방식이 바뀌었다.

## 프루닝과 캐시 재배분

Pruning은 설정된 정책에 따라 불필요한 데이터를 정리하는 작업이다. 디스크가 부족해질 때만 자동으로 오래된 블록을 지우는 뜻은 아니다.

- 상태 프루닝: 과거 계좌·계약 상태를 조회하는 데 필요한 상태 데이터를 정리.
- 히스토리 프루닝: 오래된 블록 본문·영수증 같은 기록을 정리. 헤더는 남길 수 있다.
- 오늘 본 NoPruning은 상태 데이터 보존과 관련된다. 저장공간을 위해 오래된 블록 기록을 정리하자는 앞선 관심사는 히스토리 프루닝과 구분한다.

hash 방식에서 프루닝을 끄는 아카이브 모드는 블록 처리마다 상태를 디스크에 커밋한다. 저장을 미루며 불필요한 상태를 정리하기 위한 Dirty 캐시 예산을 계속 둘 필요가 없어, Clean 캐시와 Snapshot 캐시에 돌려준다.

```go
config.TrieCleanCache += config.TrieDirtyCache * 3 / 5
config.SnapshotCache += config.TrieDirtyCache * 2 / 5
config.TrieDirtyCache = 0
```

이것은 실제 데이터를 옮기는 코드가 아니라 메모리 예산을 재배분하는 코드다. Snapshot 캐시를 쓰지 않으면 전부 Clean 캐시에 준다. 60:40 비율은 구현의 배분 정책이며 프로토콜 규칙이 아니다. 근거가 되는 저장 분기는 `core/blockchain.go`의 ArchiveMode일 때 `bc.triedb.Commit(root, false)`를 호출하는 부분이다.

## StateScheme: hash와 path

```go
scheme, err := rawdb.ParseStateScheme(config.StateScheme, chainDb)
```

여기서 scheme은 상태 저장 방식이다. 테이블·컬럼을 정의하는 일반적인 DB schema와 구분한다. Parse는 입력을 읽고 해석한다는 뜻이다.

- 빈 DB라면 지정한 방식을 사용한다. 설정도 없으면 현재 소스는 path를 선택한다.
- 기존 DB가 있고 설정이 없으면 기존 저장 방식을 유지한다.
- 설정과 기존 DB 방식이 다르면 자동 변환하지 않고 오류를 반환한다.

상태 트리의 노드는 루트·갈림길·데이터 지점 같은 트리의 구성 조각이다. 네트워크에 참여하는 노드와는 다른 뜻이다. DB는 이 조각들을 키→값으로 저장한다.

| 저장 방식 | 키 | 값 |
|---|---|---|
| hash | 트리 노드 내용의 해시 | 인코딩된 트리 노드 데이터 |
| path | 트리 내 위치를 나타내는 경로를 기반으로 한 키 | 인코딩된 트리 노드 데이터 |

값에는 자식 참조나 계좌 상태 등이 들어갈 수 있으며 모든 노드가 곧바로 잔액은 아니다. path 방식의 실제 키에는 트리 구분 정보도 포함된다.

hash 방식은 내용이 바뀌면 새 해시 키가 생겨 이전 버전이 남을 수 있다. path 방식은 같은 위치의 최신 내용을 갱신할 수 있으며, 과거 상태는 별도의 이력 관리가 필요하다. ParseStateScheme 자체는 실제 상태를 쓰는 작업이 아니다.

## 트랜잭션과 영수증 재정리

트랜잭션은 서명된 실행 요청이고, 영수증은 그 요청의 실행 결과 기록이다. 실행 후 트랜잭션이 영수증으로 변하는 것이 아니라 둘이 별도로 존재한다.

- 블록 바디에는 트랜잭션 원본 목록이 들어간다.
- 영수증은 성공·실패, 가스 사용량, 이벤트 로그 등을 담고 별도로 저장된다.
- 블록 헤더의 receiptsRoot는 영수증 목록에 대응하는 루트 해시다.
- 다른 노드는 원본 트랜잭션을 실행하고 결과를 검증할 수 있다.
- 유효하게 포함된 거래라도 EVM 실행에서 실패할 수 있고, 실패 영수증이 생성될 수 있다.
- 블록당 거래 수는 240개나 256개로 고정되지 않는다. 가스 사용량과 블록 가스 한도 등에 따라 달라진다.

## Lighthouse 설치 및 소스 확보

합의 계층과 실행 계층에 사용 언어가 정해져 있는 것은 아니다. Lighthouse는 Rust, Prysm은 Go다. 실행 계층에도 Geth(Go), Reth(Rust), Nethermind(C#) 등 여러 구현이 있다.

Lighthouse가 널리 사용된다고 Rust 하나가 보급의 원인이라고 단정할 수는 없다. Sigma Prime의 장기 개발·유지보수와 Rust의 메모리 안전성·성능 특성을 구분해서 이해한다. 운영에 Rust 지식이 필수인 것은 아니지만 소스 분석에는 필요하다.

오늘 확인·설치한 내용:

- Lighthouse 버전: **v8.3.2**.
- 공식 Linux x86_64 배포 파일을 `.local/lighthouse/`에 설치.
- GitHub 릴리스의 SHA256 digest와 다운로드 파일을 대조해 일치 확인.
- SHA256: `ea914e932462d6a93ad78c21377d70f995e05ac224248be0b58c2f4d6740439a`.
- 기존 Ubuntu-22.04 WSL 환경에서 `--version` 실행 성공.
- `--network sepolia beacon_node --help` 실행 확인. 실제 동기화 검증은 아님.
- 루트에 `lighthouse.ps1` 추가: PowerShell에서 WSL의 실행 파일 호출.
- 공식 저장소의 v8.3.2 소스를 `lighthouse/`에 shallow clone.
- 소스 커밋: `a376defa30470923556d91bdeb15a802e297f31f` (태그 체크아웃, detached HEAD).
- `.local/`과 `lighthouse/`는 공부 저장소의 Git 추적에서 제외.

```powershell
# 공부 저장소 루트에서 버전 확인

```

현재 Geth는 Windows, Lighthouse는 WSL에서 실행하는 구성이다. 두 프로그램은 Engine API로 연결할 수 있으나, WSL 네트워크 모드에 맞는 접속 주소와 JWT 공유 설정이 필요하다. 아직 연결하지 않았다.

Lighthouse 소스는 Windows 작업 폴더에 있고 WSL에서도 접근 가능하다. Linux 홈 디렉터리에 따로 복제한 것은 아니다. Rust 개발 환경 설치나 소스 빌드는 아직 하지 않았다.
