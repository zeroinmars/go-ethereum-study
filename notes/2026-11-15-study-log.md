# 2026-11-15 학습 작업일지

## 1. 오늘의 범위와 실제 수행

- 11월 14~15일에 걸친 이번 대화를 11월 15일에 기록한다. 11월 13일 재개 지점인 `Server.setupDialScheduler()`부터 `Server.Start()`의 마지막 부분과 `run()`의 피어 등록 분기로 범위를 옮겼다.
- 설명과 로컬 소스 확인으로 dial 설정·스케줄러 가동·TCP 연결·핸드셰이크·피어 등록의 경계를 살폈다. 사용자는 discovery 테이블과 연결된 피어 목록의 차이를 질문하고 전체 흐름을 자신의 말로 연결했다.
- 소스 검색·열람은 에이전트 수행이다. 사용자 직접 구현·노드 실행·테스트는 없었다. Geth·Lighthouse 소스는 수정하지 않았다.

## 3. 이전 혼동과 현재 상태

- `dialConfig`가 실제 연결 객체인지 질문했다. 에이전트가 설정과 연결 도구, 연결 결과를 구분해 설명했으며 이후 독립 확인은 없었다.
- `loopWG.Add(1)`이 락 때문에 기다릴 고루틴을 늘리는지 질문했다. 작업 수 등록과 `Wait()`의 대기, `Done()`의 감소를 설명했다. 동시성 이해 전체로 확대하지 않는다.
- TCP 연결 성공과 피어 등록을 같은 것으로 볼 수 있는지 질문한 뒤, 11월 15일에는 그 사이 여러 단계가 있음을 자신의 말로 연결했다. 부분 이해 관찰로 남긴다.
- 에이전트가 `checkpointAddPeer`를 “등록 전 검사 지점”이라고만 소개해 분기 전체가 등록 전 로직인 것처럼 모호하게 전달했다. 이후 그 분기 안에서 최종 검사와 실제 등록까지 한다고 정정했다. 이 혼동을 사용자 역량 부족만의 근거로 해석하지 않는다.
- `setup...` 함수들도 고루틴을 시작하므로 “초기 설정만 하고 실행은 모두 run에서 한다”는 설명은 부정확하다. 에이전트가 이 경계를 보완했지만, 마지막 설명 뒤 사용자 재표현은 아직 없다.
- 11월 13일의 UDP 소켓 이해 미확인과 기존 다음 과제는 완료로 변경하지 않는다. 이번에 관련 설명을 접한 것과 과제 통과를 구분한다.

## 4. 실무 역량 증거

- 사용자 증거는 용어의 의미 확인, 코드 단계 간 차이 질문, 설명 후 흐름 재구성이다. 독립 구현·실행·장애 분석에 해당하는 재현 가능한 산출물은 없다.
- 에이전트는 `rg`로 호출부와 구현을 확인했다. 핵심 참조는 `p2p/server.go`의 `Start`, `setupDialScheduler`, `run`, `SetupConn`, `setupConn`, `checkpoint`, `launchPeer`; `p2p/dial.go`의 `newDialScheduler`, `dialTask.dial`; `p2p/discover/table.go`의 `Table`, `bucket`이다.
- 확인한 소스 관계: 스케줄러는 후보 공급원과 `srv.SetupConn`을 받아 고루틴을 시작한다. outbound TCP 연결 성공 후 연결 처리 함수로 넘기며, `setupConn()`은 핸드셰이크 사이와 이후에 채널로 `run()`의 검사를 요청한다. `checkpointAddPeer` 분기는 검사 통과 시 피어를 가동하고 `peers` 맵에 넣는다. 실제 노드 실행으로 검증한 결과는 아니다.
- 일지 작성·검토·커밋·푸시는 사용자 요청에 따른 에이전트 작업이며 사용자 독립 수행 증거로 인정하지 않는다. Git 성공 여부는 실제 명령 결과로 별도 확인한다.

## 5. 다음에 확인할 작은 과제와 재개 지점

다음에는 `setupDialScheduler()`에서 시작된 연결이 `setupConn()`과 `run()`으로 이어지는 경로를 필요한 부분만 연결한다. 아래는 제안이며 완료 표시하지 않는다.

1. `newDialScheduler()`의 고루틴 시작과 `dialTask.dial()`의 TCP 연결 위치를 찾아 구분하기. 통과 기준: 설정·가동·개별 연결 성공을 다른 사건으로 설명한다.
2. `setupConn()`의 두 핸드셰이크와 두 checkpoint를 차례로 짚기. 통과 기준: 핸드셰이크 수행 위치와 `run()`의 검사·등록 위치를 구분하고 `c.cont`로 결과를 받는 지점까지 설명한다.
3. discovery의 `bucket.entries`와 `run()`의 `peers`를 비교하기. 통과 기준: 테이블에 노드가 있다는 이유만으로 TCP 연결·피어 등록이 완료되었다고 판단하지 않는다.

## 6. 취업 관점

- Go 기반 네트워크 코드 탐색과 비동기 처리의 책임 구분은 클라이언트 개발·노드 인프라·블록체인 백엔드 후보 직무에 관련된다. 이번 증거는 설명을 받으며 큰 흐름을 구분하는 단계에 한정된다.
- 지원을 받으며 호출 경로를 정리하는 업무에 연결할 가능성은 있지만, 독립 네트워크 구현·동시성 디버깅·노드 운영을 맡길 수 있다는 증거는 없다. 일반 개발 경력이나 다른 분야 역량은 판단하지 않는다.

## 7. 탐색 방식과 범위

- 큰 구조 파악과 개념 정리가 중심이었다. `Server.Start()`의 초기화 및 서비스 가동에서 피어 생명주기 관리로 넘어가는 흐름을 살폈고, 채널 분기와 호출부 일부를 확인했다.
- TCP 내부, 암호화 알고리즘, 핸드셰이크 메시지 구현, dial 선택·재시도 알고리즘, discovery 탐색 알고리즘 전체는 분석하지 않았다. 개발 모드·부하 테스트별 경로도 이번 범위가 아니다.

## 8. 질문·협업 방식

- 11월 14일 “Post가 암호화로 유추해야” 하는지, `AddPeer`가 등록을 중심으로 지어진 이름인지 물었다. 이름과 실제 동작 사이의 근거를 확인하는 행동으로, 코드 설명이나 설계 검토 시 용어의 모호함을 줄이는 데 도움이 될 가능성이 있다. 작성자의 작명 의도는 확인하지 않았다.
- 11월 15일 discovery에서 피어 등록까지의 흐름을 길게 재구성한 뒤, `run()` 안에서 전부 하는지와 스케줄러가 연결까지 하는지를 분리해 질문했다. 11월 13일 전체 흐름을 요약하고 경계를 확인했던 행동과 유사한 접근이 관찰됐다. 상세 구현의 독립 분석이나 업무 성과로 확대하지 않는다.
- “아직 이해가 하나도 안가네”, “기억햇다가 또 까먹거든”이라고 현재 어려움을 밝혔다. 핸드셰이크를 악수라는 원뜻에 연결하는 설명을 요청한 맥락이다. 기억 능력·성격·생산성을 판단할 근거로 쓰지 않는다.
- 에이전트 설명의 압축과 단계 표현의 모호함도 질문에 영향을 주었다. 동료와의 리뷰·역할 분담·일정 조율·문서 전달 성과는 이번 질의응답으로 입증되지 않는다. 다음 관찰 지점은 짧은 소스 경로를 도움 없이 다시 연결하는지다.
